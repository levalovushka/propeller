# Люди и проекты — спецификация слоя сущностей

Статус: **спека, ничего не реализовано.** Собрана 2026-08-18 по интервью с
владельцем (три круга) поверх замеров диаризации
([`tools/diarize-lab/DIARIZATION.md`](tools/diarize-lab/DIARIZATION.md)).
Дальше по решению владельца: **потолок наименования → слой связей → остальное**,
и перед стройкой — дизайн и вайрфреймы.

## 1. Зачем это, одной фразой

Чтобы собирать и обрабатывать **сквозной контекст между встречами**. Человек и
проект — не разделы, а **атрибуты встречи**; разделы появляются только как
поверхность управления ими.

Заявленная владельцем ценность — все четыре сразу:

| # | ценность | что для неё нужно |
|---|---|---|
| Ц1 | имена вместо `Speaker N` в ленте и конспекте | связь **кластер → человек** |
| Ц2 | исполнители в «Задачах» | она же |
| Ц3 | поиск и история по человеку («что мы решали с Радиком») | связь **встреча ↔ человек** |
| Ц4 | контекст перед встречей (кто это, о чём договорились) | она же |

**Ц3 и Ц4 не требуют наименования вообще.** Это главный вывод спеки: половина
ценности достигается связью «встреча ↔ человек», которая на 66 % архива уже
лежит на диске.

## 2. Что это НЕ, и почему это не отмена прошлого решения

`product-ideas.md`, раздел «Убито»: **библиотека голосов / People /
voice-matching** — убиты, причина «install & forget». Спека их не возвращает:

| убито | здесь |
|---|---|
| voice-matching, эмбеддинги человека между встречами | **нет вовсе.** Идентичность — из календаря и от человека, никогда из голоса |
| `PeopleStore` как база голосов | человек — запись из адресов и имён, без акустики |
| пост-транскрипционный опрос «опознай спикеров» | **приложение не спрашивает ни разу.** Состав ставится молча из календаря; правка — возможность, не вопрос |
| вкладка Speakers как обязательный шаг | поверхность управления, куда заходят редко и по своей воле |

Отличие в одном: тогда механизмом был **голос**, и он требовал обучения от
человека. Здесь механизм — **календарь**, и он не требует ничего.

## 3. Измеренные факты, которые связывают руки

Все числа — этой сессии, на живом архиве владельца (59 встреч). Не повторять
замер, а ссылаться.

| факт | число | следствие для спеки |
|---|--:|---|
| встреч с календарной привязкой | 39 из 59 (**66 %**) | связи есть почти бесплатно на двух третях архива |
| встреч **без** события | 20 (34 %) | треть — вручную, автоматике недоступна |
| приглашённых против говоривших кластеров | **315 против 79** | приглашённые вчетверо шире правды |
| встреч, где приглашённых больше кластеров | 32 из 38 (84 %) | «приглашён» ≠ «был» ≠ «говорил» — три разных факта |
| «приглашённых − владелец == кластеров» | 5 из 38 (**13 %**) | по числу кластеров состав не восстановить |
| уникальных людей в рабочих созвонах (≤8 приглашённых) | **34**: 14 своих, 20 внешних | набор маленький |
| внешних, встретившихся ровно один раз | **14 из 20** | ~5 новых лиц в неделю |
| адресов только в больших рассылках (>8 приглашённых) | **108** | в список людей их пускать нельзя |
| адреса, из которых выводится имя | 16 % (+4 % только фамилия) | **80 % — непрозрачные инициалы**, и это свой домен |
| одна локальная часть на разных доменах | 6 (`vla@nds.et` / `vla@pragmatica.design`) | адрес как ключ даёт ложные склейки |
| один клиент под двумя доменами | `theact.ru` + `theact-labs.com` | домен → проект без ручной склейки не работает |
| `gmail.com` в рабочих созвонах | 16 встреч | как ключ проекта не значит ничего |
| повторяющихся событий | 7 из 59 | серия события покроет мало |
| упоминаний имён в дальней речи (встреча ГПН) | **9 на 769 реплик**, в микрофоне владельца **0** | имена из речи не вытащить |
| главный голос встречи назван по имени | **ни разу** (38 % времени) | ведущего не окликают по построению |
| «меня зовут» / «представлюсь» во всём архиве | **1 встреча из 59** | представлений нет |
| реплик архива под `Speaker N` | 10 675 из 18 688 (**57 %**) | размер Ц1 |
| чистота кластера на средней встрече | **97,3 %** | имя, повешенное на кластер, будет верным |
| кластеров против людей на средней встрече | **4 на 5** | человек без кластера имени не получит никак |

### 3.1. Ненаблюдаемость состава — центральное ограничение

Владелец определил участника как **«все, кто реально был, даже если молчали»**.
Это правильное определение и **ненаблюдаемое**: списка участников звонка у
приложения нет и не будет (Zoom не отдаёт, заголовки окон пусты без «Записи
экрана», разрешение выкинуто из бандла). `**Participants:**` в markdown сегодня
собирается из спикеров транскрипта
([`MarkdownWriter.swift:138`](meeting-recorder/swift/Sources/MarkdownWriter.swift:138)) —
это не состав.

У молчавшего участника **нет ни одного следа в звуке** — прямо по определению.
Значит:

> Состав встречи — не выводимые данные, а **данные пользователя с машинным
> черновиком**. Календарь предлагает, человек вычёркивает, и до тех пор состав
> равен списку приглашённых.

Это решение владельца («если человек сам не убирает, указываем всех
приглашённых пока что») и цена его названа: поиск по человеку будет вчетверо
шире правды, пока никто не правил. Это осознанный обмен точности на отсутствие
вопросов.

## 4. Сущности

### 4.1. Человек

Решение владельца: **сущность со списком адресов**.

| поле | что это |
|---|---|
| id | стабильный внутренний, не почта |
| имя | то, что видно в ленте и конспекте; редактируется |
| адреса | список; из календаря и от человека |
| алиасы имени | как его зовут вслух («Лёша» при «Алексей») — вход для стирания и для будущего наименования |
| свой / внешний | выводится по домену; влияет на видимость, не на права |
| первая и последняя встреча | для «показывать не всех» |

Склейку двух записей **предлагает приложение, решает человек** (6 замеренных
ложных кандидатов — причина, почему не автоматически).

### 4.2. Связь «встреча ↔ человек» — три разных факта, не один

Замер 315/79 требует различать. Хранить как три состояния одной связи:

| факт | откуда | когда появляется |
|---|---|---|
| **приглашён** | `CalendarMeta.attendees` | сразу, молча, 66 % встреч |
| **был** | приглашён минус вычеркнутые человеком | по умолчанию = «приглашён» |
| **говорил** | кластер → человек | только когда наименование решится |

Ц3 и Ц4 стоят на «был». Ц1 и Ц2 — на «говорил». Их нельзя смешивать в одно
поле: сегодняшний состав — догадка, и он не должен выглядеть как факт.

### 4.3. Проект

Решение владельца: **базово руками, механику делать умнее постепенно; проекты —
отдельный разговор.** Здесь только место под них и то, что уже известно:

- домен участников как подсказка — слабая (`gmail.com` в 16 встречах,
  один клиент под двумя доменами);
- серия события — покроет 7 встреч из 59;
- поэтому: проект заводит человек, приложение **предлагает** по домену, серии и
  составу, склейку доменов решает человек.

Проект нужен спеке людей в одном месте: встречи **без календаря** (34 %)
получают людей «вручную плюс подсказка через проект» — то есть **Ц-путь для
трети архива зависит от проектов**. Пока проектов нет, у этой трети люди
появляются только вручную. Это записанная зависимость, а не недоделка.

## 5. Наименование: кластер → человек

Что уже известно и не надо переоткрывать:

- **голосом нельзя** — библиотека убита;
- **из речи нельзя** — 9 упоминаний на 769 реплик, главный голос не назван;
- **из представлений нельзя** — 1 встреча из 59;
- **по числу кластеров нельзя** — совпадает в 13 %;
- **чистота кластера достаточна** (97,3 %), узкое место не в разметке;
- **полнота кластеров недостаточна** (4 на 5): у человека может не быть кластера.

Остаётся одно: **модель читает встречу и назначает**, имея состав как список
кандидатов. Это гипотеза, и она замеряется до стройки — шаг «потолок» ниже.

Правила, которые спека фиксирует независимо от результата замера:

1. **Наименователь обязан уметь сказать «не знаю»** — и про кластер, и про
   человека. Раздать все имена по всем кластерам значит вернуть выдуманного
   исполнителя, только теперь с настоящим именем: это **хуже**, чем `Speaker S2`.
2. **Кластер весом в несколько секунд не называется.** Для этого наверх должен
   уходить вес кластера, которого сейчас нет (см. §8).
3. **Имя, поставленное человеком, сильнее машинного** и не перезаписывается
   никогда.
4. **Порядок кластеров ничего не значит.** `Speaker S1` — не «первый по
   важности», и связывать его с порядком в списке приглашённых нельзя.

### 5.1. Подпись одним движением

Решение владельца по ленте: **подписать одним движением.** Механика:

- пока имени нет, в ленте остаётся `Speaker S1` — как сейчас;
- клик по подписи открывает состав встречи; выбор переписывает **все** реплики
  этого кластера сразу, в ленте и в конспекте;
- это возможность, а не вопрос: приложение не подсвечивает, не считает
  неподписанные кластеры и не напоминает;
- обратимо (⌘Z), потому что ошибка стоит переписанной ленты.

Это то, что отличает конструкцию от убитого опроса: **инициатива у человека,
и молчание — законный конец.**

## 6. Задачи и исполнители

Решение владельца: **только прямые обещания с высокой уверенностью, либо без
исполнителя вовсе; проверка по составу.**

| случай | исполнитель |
|---|---|
| «я сделаю» с микрофона владельца | владелец — он известен по построению |
| человек назван в тексте прямым адресом («Ира, соберёшь?») и есть в составе | этот человек |
| кластер подписан человеком вручную | подписанный |
| всё остальное | **исполнителя нет** |

Проверка по составу — жёсткий фильтр: имя, которого нет в составе встречи, в
«Задачи» не попадает. Это продолжение уже работающего `RecapLint.grounded`,
которому не хватало именно списка законных имён.

## 7. Поверхности

Решение владельца: **внутри встречи + отдельный раздел как настройки для
управления.**

| поверхность | что делает | чего не делает |
|---|---|---|
| строка участников в карточке встречи | показывает состав, даёт вычеркнуть и добавить | не спрашивает, не мигает, не блокирует |
| подпись кластера в ленте | §5.1 | не предлагает сама |
| раздел управления (как настройки) | люди, склейки, проекты, видимость | не место для рутины: заходят редко |
| фильтр встреч по человеку | Ц3 | — |

Полезное: контрол фильтра **уже существует** в дизайн-системе —
`MeetingsTitleBlock` принимает `speakerOptions` / `selectedSpeaker`
([`MeetingsTitleBlock.swift:19`](meeting-recorder/swift/PropellerUI/MeetingsTitleBlock.swift:19))
и не подключён ни к чему. Ц3 — это подключение, не новый экран.

### 7.1. Одноразовые люди

Решение владельца: **заводить всех, показывать не всех.** Запись есть у каждого,
в списке видны встретившиеся дважды и больше; остальные находятся поиском.
Порог — «вторая встреча», и он выведен из замера: 14 из 20 внешних за три недели
встретились один раз.

Отдельным правилом: **адреса из событий с >8 приглашённых не заводятся** (108
адресов в архиве). Рассылка — не встреча.

## 8. Что нужно от кода, чего сегодня нет

Наружу из диаризации уходит только строка `speaker` в `PersistedSegment`.
Этого не хватает трём местам спеки:

| нужно | зачем | кто ждёт |
|---|---|---|
| **id кластера** отдельно от подписи | чтобы «подписать одним движением» знало, какие реплики переписать; сейчас идентичность кластера закодирована в самой строке `Speaker S1` | §5.1 |
| **вес кластера** (секунды, число реплик) | чтобы наименователь отказался называть кластер на 9 секунд | §5, правило 2 |
| **список законных имён** для рекапа | фильтр «имени нет в составе» | §6 |

Первые два — это ровно пункт 2 «технического инкремента» первого блока, и его
формат теперь определён: не просто вес, а `(id, вес)` рядом с подписью.

## 9. Приватность и стирание

Сегодня `PersonErasure` устроен на прямом допущении: «у человека в этой модели
данных **нет объекта** — есть имя, лежащее текстом в девяти местах»
([`PersonErasure.swift:3`](meeting-recorder/swift/PropellerPure/PersonErasure.swift)).
Спека это допущение отменяет, значит стирание меняется:

- стереть человека = удалить запись, все связи, все адреса **и** прогнать
  текстовое стирание, как сейчас;
- список алиасов человека (§4.1) становится **входом** стирания вместо ручного
  списка форм — то есть точность стирания вырастет;
- ограничения текстового стирания остаются как есть и названы в его doc-комменте
  (двое стёртых становятся одним, падежи не восстанавливаются, перестраховка
  сильнее пропуска);
- retention аудио к людям не относится и не меняется.

**Это надо перечитать перед реализацией стирания**, а не после: цель D роадмапа
уже обещала «стереть человека», и обещание нельзя ослабить появлением сущности.

## 10. Порядок работ (решение владельца)

1. **Спека целиком** — этот файл. Дальше правится по дизайну, не по ходу стройки.
2. **Потолок наименования** — один прогон, до любой стройки. Что мерить:
   на встречах с эталоном дать модели транскрипт с `Speaker N` плюс состав и
   спросить назначение. Метрика: сколько кластеров названо верно и сколько
   **названо неверно** — второе дороже первого. Сначала оракулом (Sonnet): если
   не может он, направление закрыто одним прогоном. Потом локальная модель на
   том же входе. Стенд — `tools/recap-lab`, решётка {модель} × {вход} уже есть.
3. **Слой связей** — встреча ↔ человек, «приглашён» / «был», список, фильтр,
   строка участников. Даёт Ц3 и Ц4 без наименования.
4. **Остальное** — Ц1, Ц2, подпись кластера, исполнители, проекты.

Между 1 и 3 — **дизайн и вайрфреймы** (решение владельца: «его нужно ещё
допродумывать и порисовать»).

## 11. Чем проверим, что работает

Не «выглядит хорошо», а числа, которые можно взять:

| ценность | метрика | откуда брать |
|---|---|---|
| Ц1 | доля реплик под `Speaker N`: сейчас **57 %** | индекс архива, одна строка кода |
| Ц2 | доля задач с исполнителем **и** доля задач с неверным исполнителем | golden `tools/recap-lab` |
| Ц3 | доля встреч, у которых состав непуст: сейчас **66 %** потенциально | индекс |
| Ц3 точность | доля состава, вычеркнутого человеком (чем меньше, тем ближе черновик к правде) | телеметрия правок |
| наименование | верно названных кластеров / неверно названных | шаг 2 |

**Замер Ц1 и Ц3 нужно снять до стройки**, чтобы «стало лучше» имело базу.

## 12. Открытые вопросы, требующие решения владельца

Не догадки — то, что интервью не закрыло:

1. **Что показывать в контексте перед встречей** (Ц4): состав и прошлые
   договорённости — или ещё что-то. От этого зависит, что вообще считать
   контекстом человека.
2. **Свой / внешний** — выводить по домену автоматически или спрашивать один
   раз? Домен владельца известен, но `nds.et` и `wonderpeek.com` в архиве ведут
   себя как «почти свои».
3. **Что делать с 108 адресами из рассылок**, если человек всё же хочет кого-то
   из них: искать по всему календарю или добавлять руками?
4. **Пороги видимости** (§7.1): «вторая встреча» — предложение из замера, а не
   решение.
5. **Проекты** — отдельный разговор, назначен владельцем.
