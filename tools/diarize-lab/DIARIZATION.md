# Кто говорил — доска замеров

Направление: диаризация дальней стороны. Вопрос ровно один — **есть ли здесь
что улучшать, и стоит ли выигрыш цены**. Допустимый ответ «нет».

Замеры 2026-08-18, если у строки не написано иное. Всё, что здесь названо
числом, получено в этой сессии на этой машине; всё, что взято из чужой
публикации, помечено словом «заявлено».

## Рамка

Диаризуется **только системный стем** (`TranscriptionService.diarize`,
`Sources/TranscriptionService.swift:367`). Владелец известен по построению — он в
микрофонном стеме, — поэтому задача не «разделить всех», а «разобрать дальнюю
сторону». Кластеров может быть сколько угодно; имён у них нет и здесь не будет
(библиотека голосов и опрос убиты продуктовым решением, `product-ideas.md`).

## Где принимается решение «это другой человек»

По коду, не по докам. Движок — FluidAudio 0.15.5, `OfflineDiarizerManager`;
это порт **pyannote community-1** (powerset-сегментация + WeSpeaker + VBx),
так написано в их README и так называются дефолты в `OfflineDiarizerConfig`.

Приложение зовёт его с `OfflineDiarizerConfig()` — то есть на всех значениях по
умолчанию, ни одна ручка не тронута. Цепочка решений:

| шаг | что делает | значение у нас | файл |
|---|---|---|---|
| сегментация | окно 10 с, шаг 2 с (80 % перекрытия), powerset-модель говорит, кто активен в кадре 0,08 с | `windowDuration 10`, `stepRatio 0.2` | `OfflineDiarizerTypes.swift:46` |
| маска спикера | кадры перекрытия вычёркиваются из маски перед эмбеддингом | `excludeOverlap = true` | там же:100 |
| **порог годности реплики** | спикер, активный меньше **20 % окна** (≈2 с из 10) после вычёркивания перекрытия, **не получает эмбеддинга вовсе** | `minActiveRatio = 0.2`, зашито | `OfflineEmbeddingExtractor.swift:519` |
| эмбеддинг | WeSpeaker → 256 чисел → PLDA → 128 | `batchSize 32`, `minSegmentDuration 1.0` | `OfflineDiarizerTypes.swift:100` |
| **сколько людей** | AHC с центроидной связностью по косинусу 0,6 (= евклид 0,894 на нормированных), затем VBx с тёплого старта (Fa 0,07, Fb 0,8, 20 итераций) **переопределяет число кластеров** | `threshold 0.6`, границ min/max/num нет | `AHCClustering.swift:56`, `OfflineDiarizerManager.swift:251` |
| сборка | по кадрам: сколько людей ожидается, столько верхних кластеров и берётся; **кадр без голосов достаётся кластеру 0** | `zeroVoteReembed` выключен | `OfflineReconstruction.swift:171` |
| перекрытия наружу | одновременная речь подрезается, наружу один человек в моменте | `exclusiveSegments = true` | `OfflineDiarizerTypes.swift:187` |
| **склейка с репликами** | реплика получает метку окна, внутрь которого попала её **середина**; нет такого окна — метку ближайшего по центру | — | `PropellerPure/PropellerPure.swift:205` |

Что из этого следует про короткие реплики и перебивания, до всяких замеров:

- **Реплика короче ~2 с внутри окна не голосует за своего человека.** «Угу»,
  «да», «а можно вернуть» не создают эмбеддинга, значит не могут ни создать
  кластер, ни попасть в свой.
- **Перебивание вычитается дважды**: сначала из маски эмбеддинга
  (`excludeOverlap`), потом из вывода (`exclusiveSegments`).
- **Кадр, за который никто не проголосовал, отдаётся кластеру 0** — то есть
  чужая реплика молча всасывается в самого разговорчивого. Это ровно тот
  механизм, которым «Speaker S1 содержал двоих».
- **Ошибка склейки живёт отдельно от ошибки кластеризации**: даже при идеальных
  границах реплика на стыке двух ходов достаётся тому, чьё окно накрыло её
  середину.

## Корпус: две встречи, и это не выбор, а всё что есть

`retention` включён по умолчанию (коммит 4d52602) и **съел звук архива**: в
индексе 55 встреч, стемы живы у двух. Пресейл `20260812_144201`, на котором
прошлая сессия видела двоих в одном кластере, существует только текстом.

| id | длина | что за встреча | людей с дальней стороны |
|---|--:|---|--:|
| `20260817_160113` | 30,5 мин | звонок про дизайн; второй человек с той стороны говорит в начале и в конце | 2 |
| `20260817_165425` | 68,4 мин | портал ГПН: презентация плюс обсуждение, у каждого свой микрофон | 5 |

Владелец назвал вторую **средней по сложности** — то есть именно её и надо
отрабатывать хорошо. Она же и главная линейка ниже.

Уязвимость метода записана здесь, а не в выводах: **корпус скоропортящийся**.
Через месяц retention съест и эти две. Любая будущая проверка гипотезы должна
начинаться с «а есть ли на чём мерить», и стемы надо утаскивать в лабораторию в
день записи.

## Эталон

Размечен руками по расшифровке системного стема: свежий ASR (`gigastt`,
`segments=true`), 350 и 769 реплик, каждой сопоставлен человек — по обращениям
(«Илья», «Лёша», «Юрий»), по ролям, по связности хода. Где текст не решает —
`?`, и такая реплика **вне зачёта**.

| | дальней речи | размечено | доля |
|---|--:|--:|--:|
| `160113` | 722 с | 614 с | 85 % |
| `165425` | 2371 с | 2170 с | 92 % |

Чего этот эталон не может, честно:

1. **Границы взяты у ASR, а не поставлены на слух.** Значит «пропуск» и «ложная
   тревога» в DER мерят не диаризатор, а совпадение двух разных VAD. Поэтому
   ниже есть вторая метрика.
2. **Разметка велась диапазонами реплик.** Короткая вставка внутри длинного хода
   могла остаться подписанной хозяином хода. Такая ошибка **штрафует правого
   диаризатора**, а не покрывает неправого, — то есть смещает результат в
   сторону «диаризация плоха», а вывод здесь делается в обратную. Все
   расхождения крупнее секунды перечитаны по тексту поштучно (см. разбор ошибок
   ниже) — на встрече ГПН правым оказывался эталон.
3. **Слушать не слушали.** Голоса не сверялись на слух; для реплик без
   содержания («угу») эталон и не пытается решать.

## Чем меряем — и почему не одним DER

**SAER** (`saer.py`) — доля времени дальней речи, ушедшей в ленте не тому
человеку. Считается по тому же правилу, что в пайплайне: середина реплики →
метка окна (`DiarizationMerge.speakerLabel`), кластеры сопоставлены людям жадно
по общему времени. Это то, что человек видит в ленте.

**DER** (`probe der`) — реализация самой FluidAudio (`DiarizationDER`,
определение NIST/pyannote, венгерское сопоставление, коллар 0). Нужен, чтобы
сравниваться с опубликованными числами. Гипотеза перед счётом обрезается по
речи эталона (`--scope ref`), иначе «ложная тревога» считает нашу же разметку.

Почему главная метрика — SAER, а не DER: диаризатор в этом пайплайне **не
решает, где речь**. Реплики приходят от ASR, метка находится всегда (нет
накрывающего окна — берётся ближайшее). Значит `miss` и `false alarm` из DER
пайплайну не стоят ничего, а стоит ровно одно — какая метка. DER остаётся для
внешней сверки и как страховка: если он и SAER поедут в разные стороны, значит
что-то не так с эталоном.

```bash
cd probe && swift build -c release            # проба, в приложение не уезжает
probe/.build/release/probe run  X.sys.wav --out hyp.json [--threshold 0.6 ...]
probe/.build/release/probe der  --ref ref/X.sys.ref.json --hyp hyp.json
python3 saer.py --ref ref/X.sys.ref.json --hyp hyp.json --utts asr/X.sys.utts.json
```

## Как сейчас

| встреча | людей | кластеров | **SAER** | DER (путаница / пропуск) | RTF |
|---|--:|--:|--:|---|--:|
| `165425` ГПН | 5 | 5 (на размеченном — 4) | **2,7 %** | 7,9 % (2,1 / 5,8) | 0,0024 |
| `160113` | 2 | **1** | **7,8 %** | 31,8 % (0,0 / 31,8) | 0,0035 |

Читается так: **на средней по сложности встрече диаризация почти не ошибается**
— 97,3 % времени дальней речи подписано верным кластером. На встрече `160113`
она сливает двоих в одного, и вся речь второго (48 с) уходит первому.

Пропуск 31,8 % на `160113` и 5,8 % на ГПН — это не «диаризатор потерял речь»,
а разница VAD плюс подрезка перекрытий; для ленты она бесплатна, потому что
метку реплике всё равно назначает ASR-время. Именно поэтому DER здесь только
для сверки.

**Диаризация бесплатна.** 6,4 с на 30 минут и 9,9 с на 68 минут — RTF 0,002–0,004
против 0,027–0,033 у самого ASR. Аргумент «дорого» не работает ни в какую
сторону: ни экономить нечего, ни платить нечем.

### Из чего сложены 58 с ошибки на встрече ГПН

Все 34 реплики перечитаны. Три семейства, и они разной природы:

| | секунд | что это |
|---|--:|---|
| ALEX ↔ IRA | 33 | **настоящая путаница двух людей**: ход Алексея на 2985–3994 с целиком уехал в кластер Иры, и в обратную сторону тоже (4054–4061). Локализовано во времени |
| YURI | 9 | **человека нет вовсе**: пятый участник сказал 9 с одной вспышкой (1727–1744 с), кластера ему не досталось, всё ушло Тоне |
| крошки на стыках | ~12 | «Да,», «Тогда», «вы?» короче секунды — середина реплики попала в окно соседа. Это ошибка склейки, не кластеризации |

То есть на средней встрече из 2,7 % ошибки **1,5 % — один перепутанный ход**,
0,4 % — человек с девятью секундами речи, 0,6 % — крошки на границах.

## Проверенные гипотезы

Все прогоны детерминированы: тот же вход и та же конфигурация дают тот же
результат, поэтому «разброс» здесь не при чём, разница в 0,1 пп — это разница.

| # | гипотеза | ГПН SAER | `160113` SAER | вывод |
|---|---|--:|--:|---|
| — | как сейчас | 2,7 | 7,8 | — |
| H1 | порог кластеризации 0,55…0,9 | 2,7 | 7,8 | **инертен**: плато, ни одного изменения на всём диапазоне |
| H1′ | порог 0,3…0,54 | 61,4 | 7,8 | **обрыв**: на ГПН всё сваливается в один кластер |
| H2 | `minSpeakers = 5` | 2,7 | — | без изменений |
| H3 | `numSpeakers` жёстко (5 / 6 / 2 / 3) | 2,7 / 9,5 | 7,5 / 33,3 | принуждение либо ничего не даёт, либо вредит |
| H4 | `zeroVoteReembed` включить | 2,7 | 7,8 | **без изменений на обеих** — кадров с нулём голосов столько, что не видно |
| H5 | `minSegmentDuration` 1,0 → 0,5 | **2,5** | 7,8 | +0,2 пп на одной встрече, 4 с из 2170 |
| H6 | `stepRatio` 0,2 → 0,1 (вдвое дороже) | 2,6 | — | шум за двойную цену |
| H7 | `exclusiveSegments = false` | 2,6 | 7,8 | ничего |
| H8 | `excludeOverlap = false` | 5,8 | — | **вдвое хуже** — дефолт подтверждён замером |
| H9 | gigastt / WeSpeaker вместо FluidAudio | **51,9** | 13,7 | 14 голосов на пятерых. Закрыто |
| H10 | Sortformer (NVIDIA, сквозной) вместо | **24,1** | **5,7** | вдевятеро хуже на средней встрече |

**Ручки кончились.** Лучшее достижимое перебором конфигурации — 2,5 % против
2,7 % на ГПН и 7,8 % без изменений на `160113`. Ни одна ручка не трогает ни
один из трёх источников ошибки: перепутанный ход Алексея, отсутствующий Юрий и
крошки на стыках.

### Порог стоит близко к обрыву — и это стоит записать

На ГПН между 0,54 и 0,55 встреча из пяти кластеров превращается в один
(SAER 2,7 % → 61,4 %). Отгруженное значение 0,6 отстоит от обрыва на 0,06, а
плато тянется до 0,9. Поднять порог до 0,7 было бы бесплатно на обеих
встречах и отодвинуло бы от обрыва в три раза. **Не делаем**: две встречи —
не основание перекручивать значение, откалиброванное авторами pyannote на
корпусе, а «на моих двух ничего не изменилось» — не доказательство, что не
изменится на чьей-то третьей. Записано как известный риск, не как задача.

### Sortformer: единственная гипотеза, которая где-то выиграла

`OfflineSortformerDiarizer` лежит в FluidAudio 0.15.5, лицензия NVIDIA Open
Model License (без ограничений на коммерцию), модели тянутся с HuggingFace,
RTF 0,0022–0,0025.

| | как сейчас | Sortformer |
|---|--:|--:|
| ГПН (5 человек) | **2,7 %** | 24,1 % |
| `160113` (2 человека, сливаются) | 7,8 % | **5,7 %** |

На `160113` Sortformer **находит второго человека**, которого community-1 не
видит: его речь из «100 % не туда» становится «49 % не туда», ценой 12 с
главного голоса. На ГПН он проваливается: у модели **жёстко четыре слота
спикеров** (`numSpeakers: Int = 4`, константа), пятый теряется, а Тоня
рассыпается пополам (277 с из 549 не туда).

Отсюда единственная выжившая идея — не замена, а **подпорка**: звать Sortformer
только тогда, когда community-1 вернул один кластер на дальнюю сторону.
Не сделано, и вот почему: доказательная база — **одна встреча**, а цена — вторая
модель в бандле, второй сетевой путь загрузки, второй источник падений и
развилка «какой разметке верить», которая расходится во всё, что ниже. Правило,
выведенное из одного примера, — не правило.

Два факта, которые закрывают направление «взять что-то получше»:

1. **Мы уже стоим на актуальной открытой SOTA.** FluidAudio 0.15.5 — последний
   релиз (07.07.2026, проверено по GitHub API), и его offline-путь это и есть
   pyannote community-1. Обновляться некуда, менять на что-то открытое —
   значит менять на худшее, и это замерено, а не предположено.
2. **Опубликованных чисел на русском и на созвонном звуке нет ни у кого.** Все
   цифры выше — AMI, CallHome, DIHARD, VoxConverse: английский, телефон,
   микрофон в переговорной. Независимый бенчмарк (arXiv 2509.26177) добавляет
   только то, что pyannote конкурентоспособен в офлайне и что **у всех систем
   ошибка растёт с числом людей**. Значит любое «а вот эта модель лучше» для нас
   проверяется только своим замером на своём корпусе — и корпус скоропортящийся.

## Граница задачи: что диаризация должна отдать наверх, чтобы приклеить имена

Диаризация отвечает «сколько людей и где чьи реплики». Имена — отдельная
работа, здесь она не делается. Но замер по ней высказался, и это главный
результат сессии.

**58 % реплик без имени — это не ошибка диаризации.** Проверено по всему
архиву: `Speaker N` вместо имени стоит на **10 675 из 18 688 реплик = 57 %**
(на пресейле 12.08, где сняли исходные 58 %, — 76 %; на ГПН — 67 %; на
`160113` — 53 %). Это ровно та доля, которую занимает дальняя сторона: у
владельца имя есть по построению, у остальных его негде взять. **При DER = 0
эта цифра не изменится ни на пункт** — идеальные кластеры всё так же будут
называться «Speaker S1».

Что для наклейки имён уже готово, а что нет:

- **Чистота кластера** — 97,3 % на средней встрече. Имя, повешенное на кластер,
  будет верным для 97 % его времени. Готово.
- **Полнота набора** — 4 кластера на 5 человек на ГПН, 1 на 2 на `160113`.
  Человек, у которого нет кластера, имени не получит никаким способом. Это и
  есть настоящий долг диаризации перед наименованием — **не точность, а
  непропущенность**.
- **Стабильность метки внутри встречи** — да, `Speaker N` держится от начала до
  конца (VBx кластеризует всю встречу разом, не онлайн).
- **Стабильность между встречами** — нет и не планируется: библиотека голосов
  убита продуктовым решением. Значит имя придётся выводить из самой встречи
  каждый раз.
- **Чего не хватает наименователю** — привязки кластера к произнесённому имени.
  Материал в звуке есть: на ГПН люди зовут друг друга по имени («Илья», «Лёша»,
  «Ира», «Юрий», «Тоня»), и в календаре встречи есть список участников. Ни то,
  ни другое диаризация сейчас наверх не отдаёт: наружу уходит только
  `speaker: "Speaker S1"` в `PersistedSegment`. Что понадобится добавить —
  ничего в самой разметке; понадобится **читатель обращений** и доступ к
  участникам события календаря.

## Вывод

**Заниматься диаризацией не стоит.** Числа, на которых это держится:

1. На встрече, которую владелец назвал средней по сложности, **SAER 2,7 %** —
   97,3 % времени дальней речи подписано верным кластером. Из этих 2,7 % больше
   половины — один перепутанный ход одного человека.
2. **Ручки инертны.** Одиннадцать проверенных гипотез, лучший результат
   2,5 % против 2,7 %. Ни одна не трогает ни один из трёх найденных источников
   ошибки.
3. **Менять движок некуда.** Мы уже на актуальной открытой SOTA (pyannote
   community-1 через FluidAudio 0.15.5, последний релиз). Оба замеренных
   кандидата хуже на средней встрече: gigastt 51,9 %, Sortformer 24,1 %.
   Лучший закрытый коммерческий движок мира по своим же заявлениям дал бы
   2,7 % → ≈2,0 %: 0,7 пп за €0,1 в час и отказ от офлайна.
4. **Цена уже нулевая** — RTF 0,002–0,004. Оптимизировать нечего.
5. **Продуктовая боль лежит не здесь.** 57 % реплик архива без имени — это
   дальняя сторона, у которой имени негде взять; при идеальной диаризации
   цифра та же. Задача «Задачи пустые или с выдуманным исполнителем» решается
   наименованием, а не разметкой.

Что остаётся известным и незакрытым — записано, но не как задача:

- **Одна встреча из двух ломается**: `160113`, два человека в одном кластере,
  7,8 %. Sortformer её частично чинит (5,7 %) и одновременно рушит среднюю
  встречу. Подпорка «Sortformer, когда кластер один» — единственная выжившая
  идея, и она стоит второй модели в бандле при доказательной базе из одной
  встречи. Возвращаться к ней имеет смысл, только если у кого-то соберётся
  корпус таких встреч.
- **Порог 0,6 стоит в 0,06 от обрыва** (см. выше). Не крутим.
- **Корпус скоропортящийся**: retention съел звук 53 встреч из 55. Откладывать
  стемы теперь есть чем — `snapshot.py`, каталог `~/diarize-lab-corpus` вне
  репозитория. На 2026-08-18 отложено **7 встреч, 0,92 ГБ** (13–68 мин): те две,
  на которых стоят числа доски, и пять записанных в тот же день. Среди новых —
  второй кандидат на слипание, `20260818_140424`: 50,8 минуты и **один кластер**
  на дальней стороне. Один это кластер потому, что собеседник один, или потому,
  что двоих слепило, — не размечено; если вопрос слипания когда-нибудь
  переоткроют, начинать с него.
- **macOS 14 `SIGBUS`** этой работой не затронут: причина в `runFbankBatch`,
  ущерб ограничен счётчиком попыток, машины для воспроизведения нет
  (STATE, `macos14-fbank`).

## Финал · 2026-08-18 — направление закрыто

Улучшать нельзя тем, что есть под рукой, и не нужно тем, что можно купить:
на средней встрече ошибка 2,7 % и она не в том месте, где болит продукт.
Лаборатория остаётся рабочей — `probe` + `saer.py` + два эталона, — чтобы
следующая гипотеза стоила один прогон, а не неделю. Следующая работа по
атрибуции — **имена**, не кластеры.

# Продолжение · 2026-08-19 — чужой опыт и обход через интерфейс звонилки

Направление «улучшать диаризацию» осталось закрытым. Ниже — два захода, которые
пришли с другой стороны: как ту же задачу решают другие и можно ли получить имена
не из звука вовсе.

## Как это решают другие

Продукты отличаются не качеством диаризации, а тем, **чем они покупают
атрибуцию**. Семейств четыре.

| семейство | кто | чем покупает | доступно нам |
|---|---|---|---|
| бот в звонке | Fireflies, Fathom, tl;dv, Read.ai, инфраструктура Recall.ai | платформа отдаёт **аудио по каждому участнику отдельно**, диаризации нет вовсе | нет: бот виден в списке, звук в облаке |
| чтение клиента локально | **Granola** (Zoom на macOS, Meet через расширение) | активный спикер и имена читаются из окна звонилки через «Универсальный доступ» | **да — замерено, см. ниже** |
| микрофон против системного звука | **Notion AI Meeting Notes**, Granola без разрешения | `Me` / `Them`; имя второго — из календарного события | уже есть у нас, это наш `SpeakerAttribution.stems` |
| отпечаток голоса | Otter, Limitless, **talat** | правка метки человеком учит отпечаток на будущее | убито продуктовым решением |

Что из этого стоит знать по пунктам:

- **Recall.ai** называет раздельные дорожки «perfect diarization» и заявляет
  «100 % точность атрибуции» — **заявление вендора, чисел нет**. В той же статье
  честно: при смешанной дорожке «системы часто отдают речь не тому спикеру», а на
  общем микрофоне в переговорке «сливают голоса в одного или теряют речь». Наш
  провал на `160113` — известный всем и аудиом не лечится.
- **Fireflies** в звонке подписывает настоящими именами, а **у загруженного файла
  даёт «Speaker 1, Speaker 2»**. Лучшее доказательство, что имена берутся из
  ростера платформы, а не из звука.
- **Notion** (обновление 2026) умеет speaker detection **только для 1:1** и берёт
  имя второго из календаря. То есть наши 4–5 кластеров при 97,3 % чистоты — впереди
  их разбора; отстаём мы в наименовании, и закрывают его тем же календарём, что
  предложен в `plan-people.md`.
- **Granola** в улучшенных заметках спикеров **не приписывает вовсе**, а в
  расшифровке без разрешения показывает `Me` / `Them`. Это ровно правило
  «наименователь обязан уметь сказать не знаю».
- **Otter**: ~**85 %** верных спикеров, на 6+ участниках ~**75 %**; отпечаток
  выучивается **из правки метки человеком**, отдельной церемонии записи голоса нет.
- **Limitless**: 20 с помеченного аудио на человека, и обозреватели описывают ровно
  ту катастрофу, от которой `plan-people.md` ставит защиту — «приписывает
  высказывания не тому и дублирует пункты задач под неверным именем».
- **talat** — прямой локальный конкурент (Mac, mic + system, без бота, разовая
  оплата) — заявляет «learns voices over time». Решение «библиотека голосов убита»
  этим не отменяется, но перестаёт быть единственно возможным.
- **DER не публикует никто.** Ни один продукт категории. Сравниваться придётся
  только со своим эталоном — и он у нас есть, это преимущество, а не долг.

## H12. Имена из окна Zoom через «Универсальный доступ»

**Гипотеза.** Granola читает активного спикера из клиента Zoom на macOS. Если это
воспроизводится, атрибуция и имена приходят готовыми, без звука, без API, без роли
хоста и без облака — на 33 из 37 встреч архива с известной платформой.

**Проба:** `axprobe/` — отдельный SPM-пакет плюс `make-app.sh`, собирающий его в
подписанный `.app`. Отчёт в `~/diarize-lab-corpus/axprobe-report.txt`.

**Замер 2026-08-19**, живая встреча Zoom 7.0.6, двое, вид «Динамик», микрофоны
включены.

Имя участника лежит в `AXDescription` **видеоплитки**, вместе с состоянием, и
панель участников для этого открывать не нужно:

```
AXTabGroup « … | Лева Ловушка, Звук компьютера включен, Video off | Обработка видео »
AXTabGroup « … | Levon Lobanov, Звук компьютера включен, Video on  | Обработка видео »
```

Активный спикер выражен **геометрией**: за 20 с и две передачи слова — шесть
изменений раскладки, говорящий получает 1080×600, молчащий сжимается до 160×80,
порядок плиток тоже переставляется (и переставлялся при равных размерах ещё до
переключения вида).

**Что стоило три негодных прогона** — записано, чтобы не повторять:

1. **Ключ по позиции узла даёт ложные изменения.** Строки и плитки
   переставляются, поэтому «Левон → Джульетта» на одной глубине — перестановка, а
   не речь. Ключевать надо по имени участника.
2. **Заглушённые микрофоны делают замер пустым.** У обоих стояло «Звук компьютера
   выключен» — активного спикера в этом случае не бывает по определению, и
   отсутствие признака говорит о микрофонах, а не о Zoom.
3. **`AXFrame` / `AXSize` были исключены как «дрожь от анимаций»** — то есть
   выброшен ровно тот сигнал, который искали. Площадь надо округлять (шаг 40 pt),
   а не игнорировать.

Плюс два факта про само разрешение, оплаченных временем:

- **`AXIsProcessTrusted()` не спрашивает и не логируется.** Без права дерево просто
  пустое; ни диалога, ни записи в `tccd`. Ручное добавление в список не сработало
  **дважды**; заработало `AXIsProcessTrustedWithOptions([kAXTrustedCheckOptionPrompt: true])`.
- **Shell-обёртка главным исполняемым файлом бандла ломает привязку TCC** — право
  уходит интерпретатору. Главным файлом должен быть сам бинарник.

**Вывод по H12: гипотеза жива и единственная из всех бьёт мимо диаризации** — но
замерена в лабораторных условиях. Владелец был организатором, участников двое и оба
он, демонстрации экрана не было. Непроверенные пункты и гейт «один прогон на
настоящей рабочей встрече» — в [`plan-speaker-tags.md`](../../plan-speaker-tags.md).
В приложение до гейта не уезжает ничего.

**Инструменты H12 построены 2026-08-19** (лабораторная часть, §11 плана; чисел
пока нет — нет ни одной живой трассы, а значит и пары «трасса + эталон»):

- `axprobe trace [--seconds N] [--interval 0.4] [--out путь]` — JSONL-трасса,
  строка на опрос; поля — контракт с `CallWindowJournal.Tile`;
- решение `PropellerPure/CallWindowJournal` (трасса → пролёты «кто говорил»),
  13 тестов по синтетическим трассам `Tests/Fixtures/ax-traces/`;
- счёт: `swift run -c release CallWindowJournalLab трасса.jsonl > journal.json`,
  затем `saer-journal.py --journal … --ref … --utts … [--fallback out/<id>.base.json]` —
  SAER в терминах `saer.py` плюс покрытие и честность; `--fallback` даёт сквозное
  число против сегодняшних 2,7 % / 7,8 %.

**Первая живая трасса — 2026-08-20** (`axprobe-trace-20260820_100341.jsonl` в
корпусе, рабочая встреча: трое, владелец — гость, вид «Галерея», 300 с / 673
опроса; параллельно встреча записана Пропеллером как `20260820_100315`, сдвиг
трассы ≈ 26 с). Три факта, один из которых поменял решение:

1. **У Zoom есть явная метка говорящего.** Хвост `AXDescription` ровно одной
   плитки на опрос кончается на `…, active speaker` — по-английски при русском
   интерфейсе («Имя, Звук компьютера включен, Video off, active speaker»).
   31 серия за 5 минут, реплики от 2,2 с. Людям то же состояние показывается
   зелёной рамкой (в виде «Динамик» на двоих рамки не было — там работает
   геометрия из замера 2026-08-19). Метка теперь главный сигнал решения.
2. **«Первое место» опровергнуто.** В галерее все плитки 520×280 (площадь
   мертва), и первая плитка совпала с меткой в **0 из 626 опросов** — правило
   удалено из решения; равные плитки без метки — молчание.
3. **Свёрнутое окно**: плитки главного окна пропадают, остаётся мини-окно с
   пустым заголовком и одной плиткой без метки (в трассе — 20,4 с, 46 опросов).
   Решение молчит; диаризация закрывает эти секунды.

Журнал решения по этой трассе воспроизводит серии метки один в один: 32 пролёта,
названо 265 с из 300 (молчание — сворачивание и стыки серий). Мьют в трассе не
встретился (у всех «Звук компьютера включен») — маркеры мьюта всё ещё пустые.

## H13. Авторизация в Zoom / Meet вместо звука — мертво

Проверено по документации 2026-08-19. Идея: попросить человека войти в звонилку и
брать состав и говорящего из API.

| путь | что даёт | почему не наш |
|---|---|---|
| Zoom Apps SDK, `getMeetingParticipants`, `onActiveSpeakerChange` | ростер и таймлайн говорения | **Host / Co-Host only**; участнику открыт только `onMyActiveSpeakerChange` — «говорю ли я», а это мы и так знаем по микрофонному стему |
| Zoom Report API `/report/meetings/{uuid}/participants` | ростер, вход/выход | Pro+ и **админский** скоуп; владелец не хост (хостят `ani@`, `pkr@`) |
| Zoom cloud recording, speaker timeline | таймлайн | Business+, хост пишет в облако, `recording:read:admin` |
| Zoom RTMS | **аудио по участникам** | публичный HTTPS-вебхук, бэкенд, **платные Developer Pack credits**, включение на уровне аккаунта |
| Google Meet REST API | ростер | `conferenceRecords.list` — **только организатору** |
| Google Meet Media API | аудио по участникам | **все участники** конференции должны быть в Developer Preview Program |

Конституция при этом не мешает (§3.4 «локально по умолчанию, облако по
обоснованию», §3.3 ростер проходит — он виден всем в комнате). Ломается об
install & forget и об роль: **у участника нет ни одного пути к таймлайну
говорения.** Единственное ценное — ростер как факт состава, и он достаётся дешевле
через H12.
