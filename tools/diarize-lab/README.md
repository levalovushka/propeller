# diarize-lab — чья диаризация лучше

**Доска замеров и вывод — [DIARIZATION.md](DIARIZATION.md)** (2026-08-18,
направление закрыто). Там эталон, метрика, одиннадцать проверенных гипотез,
внешний обзор с лицензиями и итог «заниматься не стоит» с числами. Всё ниже —
предыстория: замеры 12.08, когда эталона ещё не было.

## Из чего состоит

| | |
|---|---|
| `probe/` | SPM-проба: `probe run` гоняет только диаризатор FluidAudio с любой ручкой, `probe sortformer` — сквозную модель NVIDIA, `probe der` считает DER реализацией самой FluidAudio. `prepareModels()` не зовёт никогда (macOS 14, см. `meeting-recorder/CLAUDE.md`) |
| `saer.py` | SAER — доля времени дальней речи, подписанной в ленте не тем человеком. Главная метрика, повторяет правило склейки из пайплайна |
| `ref/` | эталон двух встреч: границы реплик и кто говорил, размечено руками |
| `mkref/` | как эталон собран: индексы реплик → человек. Пересобирает `ref/` байт в байт |
| `utts/` | границы реплик системного стема. **Только таймкоды** — текст живых встреч в репозиторий не уезжает |
| `out/` | разметки, на которых стоят числа доски: `base` (как в приложении), `sortformer`, `gigastt` |
| `snapshot.py` | откладывает стемы в `~/diarize-lab-corpus`, пока их не съел retention. Архив только читается; снимок лежит вне репозитория и в git не уезжает |
| `compare.py` | старая проба «FluidAudio против gigastt» без эталона, см. замер 12.08 ниже |

```bash
cd probe && swift build -c release && cd ..
python3 saer.py --ref ref/20260817_165425.sys.ref.json \
                --hyp out/20260817_165425.base.json \
                --utts utts/20260817_165425.sys.utts.json
probe/.build/release/probe der --ref ref/20260817_165425.sys.ref.json \
                               --hyp out/20260817_165425.base.json
```

Числа доски проверяются этими двумя командами без звука. Новая гипотеза требует
стема: `probe run <id>.sys.wav --out out/<id>.<имя>.json [--threshold …]`.
**Стемы живут в архиве владельца — только читать, копии во временные каталоги.**

## Предыстория: gigastt вместо FluidAudio

Отвечало на один вопрос: если выкинуть FluidAudio и брать спикеров из gigastt
(`?diarization=true`, WeSpeaker ResNet34 + polyvoice, модель уже лежит в
бандле), станет ли хуже. Ответ на эталоне — станет, вдвое и вдесятеро
(DIARIZATION.md, H9).

Вопрос не праздный: FluidAudio — единственный 🔴 в STATE.md. На macOS 14
кластеризация роняет процесс (`SIGBUS` в libBNNS), 29 отчётов от тестировщика,
причина не устранена, ущерб только ограничен счётчиком попыток.

## Как мерить

```bash
# сайдкар из бандла на своём порту, модели те же, что у приложения
/Applications/Propeller.app/Contents/MacOS/gigastt serve --offline -p 9891 \
  --model-dir "$HOME/Library/Application Support/Meeting Recorder/gigastt-models" \
  --pool-size 1 --inference-timeout-secs 0 --body-limit-bytes 67108864

python3 compare.py --all-short          # все встречи архива короче 25 минут
python3 compare.py 20260812_144201      # одна встреча
```

Ответы сайдкара кэшируются в `~/diarize-lab-out/<id>.gigastt.json`; повторный
запуск считает по ним и сеть не трогает.

**Эталона нет.** Руками никто не размечал, поэтому сравниваются два разбиения
одного и того же системного стема: разметка FluidAudio, лежащая в архиве
(`mergedSegmentsJSON` там, где `speakerAttribution = diarized`), против свежей
разметки gigastt. Считается число кластеров, сколько из них мельче 15 секунд, и
доля времени, где системы говорят одно и то же (кластеры сопоставлены жадно по
перекрытию). Согласие — не точность: если оба ошиблись одинаково, оно высокое.

Метки gigastt приходят на словах, а у FluidAudio в архиве лежат уже разложенные
по репликам — поэтому таблица считается дважды: по словам и после голосования
внутри реплики (реплика достаётся тому, чьих слов в ней больше). Иначе сравнение
было бы нечестным.

Четыре встречи короче двух минут дальней речи не содержат вовсе — они выпали.
Остальные восемь:

|---|--:|--:|--:|--:|
| 20260807_103402 | 5.5 | 2 | **4** (2) | 86.9 % |
| 20260810_163028 | 6.5 | 1 | **6** (4) | 55.7 % |
| 20260812_105918 | 7.4 | 2 | **6** (3) | 49.3 % |
| 20260812_110841 | 8.0 | 2 | **4** (1) | 77.7 % |
| 20260811_110211 | 10.9 | 2 | **5** (3) | 59.4 % |

Голосование по репликам меняет числа на проценты и ни одного кластера не
убирает: лишние голоса — не дрожь на словах, а целые реплики, отданные
выдуманному человеку.

Цена прохода: RTF 0.055–0.098 против 0.027–0.033 у чистого ASR — диаризация
внутри того же запроса стоит примерно ещё один ASR.

### Что это значит

**Заменить FluidAudio на gigastt как есть нельзя.** На встрече двоих он
насчитывает до четырнадцати голосов, одиннадцать из которых живут секунды.
В ленте это станет «Speaker 5», сказавшим одну фразу.

**Но и «FluidAudio точнее» из таблицы не следует.** Там, где согласие падает до
50 %, спорят не о деталях. `20260812_105918` — дейлик, где один показывает
экран, а второй поддакивает; FluidAudio свёл обоих в `Speaker S1`, gigastt
разделил на «показывает» и «угу, угу». По тексту прав скорее gigastt: реплики
«Че будет?» и «Угу, угу» принадлежат не тому, кто ведёт демонстрацию. Это тот
самый провал, ради которого в коде жил `relabelSegmentsFromStems` («на наушниках
FluidAudio сваливал всех во владельца») — правило удалено 2026-08-18 как
опровергнутое, см. DIARIZATION.md.

Итого: один дробит, другой слипает. Кто прав на конкретной минуте, без
размеченного эталона не решить — а он и так висит долгом («эталон расшифровки»,
NEXT-STEPS.md). Пятнадцать минут аудио, размеченных руками по границам реплик,
закрывают этот вопрос и заодно дают WER.

## FluidAudio 0.13.6 → 0.15.5 (2026-08-12)

Обновились и перемерили. Проба, которая гоняет **только диаризатор**, без ASR
вокруг, — отдельный SPM-пакет на 30 строк (`OfflineDiarizerManager.process` по
файлу, печатает секунды на кластер); в репозиторий не уехала, живёт в песочнице.
Весь архив — 20 часов аудио — размечается за 197 с.

Сравнивать честно можно только встречи, размеченные по системному стему
(`speakerAttribution = diarized`): у старых в архиве лежит разметка микса, это
другой вход. Таких 22.

| | встреч |
|---|--:|
| ответ не изменился | 10 |
| **нашёлся голос, которого 0.13.6 не видела** | **10** |
| голос потерялся | 2 |

Десять «нашёлся» — это ровно те встречи, где 0.13.6 сваливала двоих в одного, и
где gigastt с ней спорил: `20260812_105918` (было 1 → стало 2: 178 с и 33 с),
`20260812_153107` (1 → 2: 432 и 385 — половина встречи!), `20260812_160049`
(1 → 2: 922 и 217), `20260810_163028`, `20260811_114818`, `20260811_110211`.

Два «потерялся» важнее, чем их число. `20260812_144201` — единственная встреча
с размеченным golden, на ней говорят двое с той стороны (Милена и Саша); 0.13.6
давала 685 с и 177 с, gigastt — 899 и 120, а **0.15.5 сливает их в один кластер**
(1117 с и хвост 10 с). Второй случай — `20260807_103402`, где чужой голос
съёжился с 42 с до 12 с.

Вывод тот же, что и раньше, только резче: слипание и дробление — это не свойство
библиотеки, а свойство встречи, и без эталона мы меняем один набор ошибок на
другой. Обновление оставлено (тесты зелёные, на десяти встречах видно больше),
но **это не исправление macOS 14** — см. ниже.

### Чего обновление не чинит

Падение на macOS 14 живёт в `runFbankBatch`. По исходникам обеих версий:

- модель fbank грузится с **жёстким `.cpuOnly`** и в 0.13.6, и в 0.15.5 —
  никакой `MLModelConfiguration` снаружи на неё не влияет;
- перед батчем обе версии зовут `array.prefetchToNeuralEngine()` под
  `if #available(macOS 14.0, *)` — на cpuOnly-модель;
- в отчётах тестировщика падение приходит с очереди `com.apple.e5rt.
  concurrentExecutionQueue` (рантайм ANE) в `BnnsCpuInferenceOperation`.

То есть буфер просят подтянуть в память нейродвижка ради модели, которая на нём
не исполняется, и на macOS 14 это кончается `SIGBUS` за границей страницы. Наш
запасной заход `.cpuAndNeuralEngine` не мог помочь ни разу: до 0.15.5 конфиг
вообще игнорировался, а после — не доходит до той единственной модели, которая
падает. Кандидат в починку — эта строка prefetch, и он не у нас: либо ишью в
FluidAudio, либо форк.
