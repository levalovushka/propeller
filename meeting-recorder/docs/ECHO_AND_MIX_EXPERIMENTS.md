# Задвоенный звук: что измерено 2026-07-29

Пользователь без наушников слышит на записи чужую речь дважды. Гипотеза была
простая — микрофон ловит динамик, значит нужен эхоподавитель. Замер показал, что
виноват не столько сам факт эха, сколько **то, как мы складываем стемы**, а AEC на
нынешних дорожках попросту не может работать.

## Данные

Встреча `20260729_120234`, 43,5 минуты, микрофон и системный стем 16 кГц моно
(после фикса раздутого стема). Для транскриптов бралось окно 10:00–16:00 —
шесть минут, где говорят обе стороны. Вторая встреча (`20260728_151200`) взята как
контроль: дальняя сторона в выбранном окне почти молчит, эха нет.

Распознавание — тот же `gigastt` из бандла, отдельный инстанс на порту 9877,
`e2e_rnnt`, чтобы не мешать приложению.

## 1. Эхо в микрофоне есть, и оно громкое

| Что | Значение |
|---|---|
| Корреляция огибающих mic ↔ sys | **0.82** |
| Корреляция формы волны на лучшем сдвиге | 0.45 |
| Уровень микрофона, пока говорит дальняя сторона | **+27 dB** над собственным тихим полом |
| Слов дальней стороны, распознанных **из одного микрофона** | **95.2 %** |

Последняя строка и есть задвоение в чистом виде: gigastt читает чужую речь из
микрофонной дорожки почти целиком, как если бы её произнёс владелец.

## 2. Стемы разъехались на полсекунды — и это стабильно

Задержка mic относительно sys, замеренная по огибающим окнами по две минуты на
всей записи: **+484 мс**, разброс ±3 мс, тренд **+1 мс за час**. То есть часы двух
дорожек не расходятся; это фиксированный сдвиг старта (`Task.sleep(150 мс)` перед
SCK плюс время до первого буфера), который микшер игнорирует — он складывает с
нулевого индекса (дефект M2 в STATE.md).

Клиппинга в миксе при этом нет: 2 сэмпла на пределе из 5,7 млн (0.000 %).

## 3. Из-за этого микс теряет половину чужой речи

Шесть минут, одно и то же окно, пять условий. «Дальняя сторона доходит» — доля слов
из чистого системного стема, которые нашлись в транскрипте условия (вставки не
штрафуются: в миксе законно есть речь владельца, которой в системном стеме нет).

| Условие | Слов | Сегментов | Средняя уверенность | Дальняя сторона доходит |
|---|---|---|---|---|
| `sys` — только системный стем | 473 | 52 | 0.881 | 100 % (эталон) |
| `mic` — только микрофон | 737 | 94 | 0.887 | 95.2 % |
| **`mix` — как сейчас** | 603 | **112** | **0.826** | **52.9 %** |
| `aligned` — те же стемы, сдвиг убран | 731 | 96 | 0.881 | **95.0 %** |
| `aec` — микрофон после эхоподавления | 686 | 89 | 0.862 | 87.1 % |

Половина чужой речи не доезжает до транскрипта. Уверенность падает, сегментация
дробится вдвое. **Простое выравнивание стемов возвращает почти всё** — 52.9 % → 95.0 %,
и уверенность возвращается к уровню чистого стема.

Объяснение: две копии одной речи в полусекунде друг от друга — это не реверберация,
а второй голос, говорящий то же самое с опозданием. Когда копии совмещены, сигнал
для модели выглядит как речь в гулкой комнате, и это она переносит спокойно.

Контрольная встреча, где дальняя сторона молчит: `mix` 86.7 %, `aligned` 93.3 % при
32 словах эталона — выборка маленькая, но направление то же и деградации нет.

## 4. AEC на нынешних стемах невозможен

Когерентность выровненного системного стема с микрофоном в полосе 200–3500 Гц:
**0.04**. Для эхоподавителя это приговор — линейной связи между reference и эхом
нет, вычитать нечего.

Метрика проверена на контроле, иначе ей нельзя верить:

| Сигнал | Когерентность |
|---|---|
| Синтетическое эхо, идеальное выравнивание | 0.70 |
| То же эхо + **дрожание ±3 мс** | **0.01** |
| Наша запись (любой сдвиг 480/484/488 мс) | 0.04 |

То есть между дорожками болтается несколько миллисекунд: буферы ScreenCaptureKit
складываются подряд, а не раскладываются по своим presentation timestamp, и мелкие
пропуски сдвигают таймлайн туда-сюда. Огибающая это переживает (0.82), фаза — нет.

Собственный канцеллер (partitioned frequency-domain NLMS, 8192 отводов) на
синтетическом эхе даёт **+22 dB**, на нашей записи — **−1 dB**. Дело не в алгоритме.

## Выводы

1. **Сначала выровнять стемы в миксе** — это возвращает 42 процентных пункта чужой
   речи и стоит одного замера задержки на записи. Задержка стабильна, её достаточно
   оценить один раз по огибающим (или взять из host-time, который у нас уже есть,
   но выбрасывается).
2. **Потом чинить таймлайн по-настоящему** — класть сэмплы SCK по presentation
   timestamp, пропуски добивать тишиной. Без этого дорожки не когерентны, и любой
   эхоподавитель (наш, WebRTC AEC3, Speex) упрётся в то же самое.
3. **AEC — после пунктов 1–2 и ради прослушивания, а не ради транскрипта.** После
   выравнивания транскрипт почти не отличается от чистого стема; задвоенным остаётся
   звук в наушниках у того, кто слушает запись.
4. **Раздельная транскрипция стемов** остаётся привлекательной, но уже не как
   лечение эха: её ценность — бесплатная атрибуция говорящего (микрофон = владелец),
   нужная выпадашке участников в редизайне.

## Как повторить

Скрипты — в [`tools/echo-probe/`](../../tools/echo-probe/), нужен Python с numpy и
`ffmpeg`:

```bash
python3 -m venv /tmp/venv && /tmp/venv/bin/pip install numpy
R=~/.meeting-recorder/recordings
ffmpeg -v error -y -i $R/<id>.mic.wav -ac 1 -ar 16000 /tmp/full/mic.wav
ffmpeg -v error -y -i $R/<id>.sys.wav -ac 1 -ar 16000 /tmp/full/sys.wav

/tmp/venv/bin/python tools/echo-probe/echo_probe.py /tmp/full/mic.wav /tmp/full/sys.wav
/tmp/venv/bin/python tools/echo-probe/drift.py /tmp        # стабильность задержки
/tmp/venv/bin/python tools/echo-probe/coherence.py /tmp 7744   # линейность пути
/tmp/venv/bin/python tools/echo-probe/aec2.py /tmp 7744        # канцеллер + самотест
```

`compare2.py` считает, сколько слов дальней стороны доходит до условия, по JSON-ам
`gigastt` (`POST /v1/transcribe?segments=true`).

**Важно:** у `aec2.py` первым делом идёт самотест на синтетическом эхе. Если он не
показывает сильно положительный ERLE — числа по реальной записи бессмысленны.
