## Сквозные возможности (задевают несколько джоб)

Выносим отдельно, потому что каждая обслуживает сразу несколько джоб — детали раскрываем в соответствующих джобах.

### C1. Интеграция с Google Calendar
Пропеллер видит календарь → знает, когда начинается встреча, тянет **название** и **список участников**.
- Джоба 1 (триггер): «сейчас начнётся встреча» → предложить запись (наш ответ на Meet/Телемост, где детект процесса не работает).
- Джоба 3 (спикеры): участники встречи как подсказки для матчинга/именования спикеров.
- Джоба 4 (саммари): готовое название встречи вместо «Recording <дата>»; участники в шапку рекапа.
- **Реализовано через EventKit (2026-07-23), НЕ Google OAuth.** Полноценный OAuth требует Google Cloud проекта/ключа (нет). EventKit читает системный Календарь macOS (куда Google-календарь заводится через «Учётные записи») — без OAuth, просто разрешение как на микрофон. Честнее «локальному» духу. `CalendarService` (EventKit) + секция «Upcoming» в списке + тумблер в Settings→General. Осталось: авто-предложение записи по началу события (1.4) — детект+тайминг, пока не сделано.
- **Граница интеграции — решено (2026-07-22): только read-only, только вытягиваем.** Пропеллер тянет из Google Calendar API время встречи, название, список участников — и ничего не отдаёт обратно в облако. Ни аудио, ни транскрипт, ни саммари никогда не уходят в Google (или куда-либо в облако) — весь контент встречи остаётся локально, как и раньше. OAuth нужен только для чтения расписания; токен — в Keychain. Это ограниченное исключение из «полностью локально» (сам факт обращения к API — сетевой запрос), но контента оно не касается.

### C2. Доставка саммари в Telegram-бота — ОТЛОЖЕНО (2026-07-22)

## Джоба 1 — «Записать встречу, ничего не забыв нажать»

**Как сейчас:** 4 пути старта (Zoom-автодетект дефолт Auto, глобальный хоткей Ctrl+Opt+R, menu bar, ⌘R/кнопка). Раздельные стемы mic + системный звук (ScreenCaptureKit по всему дисплею), офлайн-микс 16кГц. Авто-стоп по концу Zoom-звонка, крэш-рекавери, mic-only деградация.

**Решения пользователя (2026-07-22):**
1. Хоткей — аудитория (менеджеры) им пользоваться не будет. Целевое — install & forget. → **убить или спрятать**, не чинить.
2. Все на Zoom — текущий автодетект ок. Но нужен ответ на **другие звонки** (Meet, Телемост): не обязательно авто-старт, а **системное уведомление с предложением включить**.
3. Стоп/отмену текущей записи смотреть у Talat («работает восхитительно») — это эталон паттерна.
4. Тестовая предзапись — **отклонено**: не перекладывать тревогу на пользователя. Правильный путь — сделать так, чтобы захват не мог молча сломаться, а не просить тестировать.
5. Приватность в целом не критична (раздаём только готовым к записи). Но: (а) на чувствительной теме нужна быстрая возможность **выключить текущую запись** из окна и менюбара — без вечного оверлея; (б) запись **всего** системного звука — реальная проблема, надо тянуть **только звук встречи**.

### Шаги

- ☑ **1.1 Убрать/спрятать глобальный хоткей.** Снять `addGlobalMonitorForEvents` и обещание «Ctrl+Opt+R» из онбординга/менюбара ([AppState.swift:132](meeting-recorder/swift/Sources/AppState.swift:132), [MenuBarPanelView.swift:69](meeting-recorder/swift/Sources/MenuBarPanelView.swift:69)). Заодно закрывает подтверждённые дефекты (нет local-monitor, нет проверки Accessibility-разрешения — хоткей молча не работал). ⌘R в фокусе окна можно оставить как бесплатный бонус. _Эффект: минус мёртвый путь и минус ложное обещание в UI._

- ◐ **1.2 Захват только звука встречи, а не всего системного звука.** **Канон 2026-07-24: ScreenCaptureKit — primary** (живой путь на Zoom). `ProcessTapAudioCapture` оставлен dormant (не hot path): Process Tap на практике давал header-only `.sys.wav` и ложные silence-баннеры. App-scoped SCK + display-wide fallback; браузер (Meet/Телемост) — позже через `meetingAppBundleIDs`. _См. [STATE.md](STATE.md) Часть 0._

- ☑ **1.3 «Стоп + удалить» для чувствительного кейса.** Кнопка/пункт «Остановить и удалить» в окне записи и в менюбаре рядом со «Стоп». Логика уже есть (`cancelRecording` → `cancelRecordingAndDiscard`, [AppState.swift:357](meeting-recorder/swift/Sources/AppState.swift:357)) — нужна только точка входа в UI. Обычный «Стоп» (сохранить+обработать) уже есть везде — не трогаем. _Эталон паттерна остановки — Talat (см. решение 3)._

- ☐ **1.4 Детект не-Zoom звонков → предложение записи (не авто-старт).** Для Meet/Телемоста детект процесса ненадёжен → основной путь идёт через **C1 (календарь): «сейчас встреча по календарю» → системное уведомление "Записать?"**. Уведомление с действием «Записать» стартует запись; бездействие — ничего. _Это же — общий механизм на любые платформы, где нет надёжного детекта процесса._

- ☑ **1.5 Автодетект: убрать хрупкость (без перекладывания на пользователя, решение 4).**
  - Убран спаун `/usr/bin/pmset` на каждый поллинг раз в 2с — заменён на нативный `IOPMCopyAssertionsByProcess` (IOKit), без сабпроцесса. Смоук-тест подтвердил рабочий вызов.
  - Детект окна-встречи без Screen Recording теперь не молчит: в Settings → Zoom meetings показывается предупреждение «Detection degraded…» + кнопка открыть настройки разрешения, когда `CGPreflightScreenCaptureAccess()` false.
  - Цель — меньше ложных срабатываний/пропусков; **без** тестовой предзаписи.

- ☑ **1.6 Гарантия целостности захвата (замена «проверке перед боем»).**
  - **Системный стем:** watchdog в `SystemAudioCapture` (4с) теперь ловит не только «нет буферов вообще», но и «буферы идут, но все тихие» — оба случая при app-scoped фильтре сначала пробуют автоматический restart на display-wide (см. 1.2), и только если это не помогло — живое предупреждение (не тег после стопа).
  - **Mic-стем:** новый `AudioRecorder.armMicIntegrityWatchdog()` — через 3с после старта проверяет, что писатель (AVAudioRecorder / VoiceProcessedMicCapture) реально продвинулся по времени записи, а не просто «isRecording=true». Если нет — `micCaptureWarning`, красная карточка в `RecordingInProgressView` с кнопкой в настройки микрофона. Раньше отвал микрофона можно было заметить только по итогу.
  - Тестовая предзапись не добавлена (по решению 4) — вместо неё контроль встроен в сам старт записи.

## Джоба 2 — «Получить точный транскрипт на русском»

**Как сейчас:** ASR — `gigastt /v1/transcribe?segments=true` (GigaAM-v3 `e2e_rnnt`); длинные файлы режутся клиентом (`GigasttChunking`, ~20 мин / body+duration caps) и мержатся; sidecar `--body-limit-bytes 67108864`. Чистка артефактов живёт **только в промпте рекапа** — сам транскрипт не чистится (`cleanASRText` только тримит). Редактирование — цельный `TextEditor`, коммит сбрасывает посегментный снапшот. Domain terms прокинуты в gigastt (`--hotwords-file`).

**Решения пользователя (2026-07-22):**
1. **Транскрипт — сырьё, не продукт.** Человек лезет в него редко и только чтобы найти конкретную деталь, которую саммари упустило; к этому моменту саммари уже готово. → **Редактирование/чистку транскрипта не делаем.** Инвестиции — в редактирование саммари (Джоба 4).
2. **Словарь терминов — делаем на 100%.** Наполняем вместе жаргоном продуктовых дизайнеров и клиентов + имена/бренды.
3. **Разрушающее редактирование — ок.** Причём доверия к разделению спикеров в целом мало: диаризацию надо делать «настолько тупой и надёжной, насколько возможно» → см. Джобу 3.

**Находка по движку (проверено в CHANGELOG/`serve --help`):** `gigastt` **умеет контекстный hotword-биасинг** — trie + shallow-fusion в greedy RNN-T, работает и на `e2e_rnnt` (BPE), и на `rnnt`. Флаги: `--hotwords-file <path>` (фраза на строку, опц. `\t<вес>`, `#`-комменты), `--hotwords-default` (встроенный русский бренд/акроним-лексикон), `--hotwords-boost <N>` (дефолт 5.0). **Конфиг на старте сервера, не per-request** (per-request «deferred»). Точка интеграции — спаун sidecar ([GigasttSidecar.swift:128](meeting-recorder/swift/Sources/GigasttSidecar.swift:128)).

### Шаги

- ☑ **2.1 Прокинуть словарь терминов в gigastt.** «Domain terms» из Settings пишется в `~/Library/Application Support/Meeting Recorder/hotwords.txt` (по фразе на строку) и подаётся в sidecar через `--hotwords-file` + всегда включённый `--hotwords-default` ([GigasttSidecar.swift](meeting-recorder/swift/Sources/GigasttSidecar.swift)). Изменение поля (дебounce 1.5с) перезапускает sidecar простым путём (`stop()` → `ensureReady()`), подпись в Settings обновлена. Смоук-тест на реальном бинарнике подтвердил `Hotword biasing enabled (32 phrase(s), boost 5)` в логе при старте.

- ☐ **2.2 Собрать стартовый словарь.** Совместно с Левоном: жаргон продуктового дизайна + типичные термины клиентов + имена команды/брендов. Я готовлю черновик глоссария (по строкам, с весами где нужно), Левон дополняет. Хранить как дефолтный пак приложения + пользовательские добавки. _Контентная задача, не код._

- ☑ **2.3 Транскрипт: редактирование и отдельную чистку НЕ делаем.** Сознательное решение: транскрипт — сырьё для поиска деталей, чистка достаточна на уровне саммари. Разрушающее редактирование остаётся как есть.

### Открытые вопросы Джобы 2
- Подтвердить прирост от hotwords на реальной записи (A/B: с `--hotwords-file` и без).
- Нужен ли per-meeting словарь (участники из календаря, C1) поверх глобального — но per-request биасинг в gigastt пока «deferred», так что только глобальный файл. Вернуться, если появится per-request.

## Джоба 3 — «Понять, кто говорил»

**Как сейчас (самая тяжёлая подсистема проекта):** FluidAudio диаризует запись в кластеры Speaker 0/1/2, потом идёт **сложный матчинг** каждого кластера против библиотеки голосов (`PeopleStore`): WeSpeaker-эмбеддинги, max-over-samples cosine, пороги, source-aware tie-break, contamination guard, дедуп, re-embed при апгрейде модели ([TranscriptionService.swift:135](meeting-recorder/swift/Sources/TranscriptionService.swift:135)). После транскрипции — `SpeakerConfirmationView` просит пользователя опознать каждого неизвестного спикера. Объём: ~2000 строк только в `PeopleStore` (874) + `PeopleSheet` (757) + `SpeakerConfirmationView` (370), плюс ссылки в 13 файлах. Раздел People — отдельный пункт sidebar.

**Решения пользователя (2026-07-22): курс на упрощение.**
1. **Раздел People в UI не нужен вообще** — «я и так знаю, с кем созванивался».
2. Единственная теоретическая ценность библиотеки — за много встреч уверенно узнавать регулярных собеседников; но ради этого выводить раздел в интерфейс не нужно.
3. **Идеал** — каждый спикер подписан своим именем. **Но если не работает — Speaker 1/2/3, консистентные в пределах звонка, достаточно.** Менеджер допишет потом.
4. Диаризацию — «настолько тупой и надёжной, насколько возможно».

### Целевая архитектура (после упрощения)

**Оставляем (надёжный пол):** FluidAudio-диаризация → консистентные Speaker 1/2/3 в пределах звонка. Это и есть «тупо и надёжно».

**Удаляем (машинерия + трение):**
- Библиотека голосов `PeopleStore` (эмбеддинги, cosine-матчинг, пороги, contamination guard, re-embed, source-aware matching).
- Раздел People + `PeopleSheet` (~757).
- `SpeakerConfirmationView` — пост-транскрипционный опрос «опознай спикеров» (~370): противоречит install & forget. Побочный эффект: `pendingSpeakers` всегда пуст → транскрипт **всегда авто-сохраняется** без ручного шага (ровно то, что нужно).
- Settings → вкладка Speakers (пороги/калибровка).
- Итого ~2000 строк удаляется; правки-удаления в ~13 файлах (риск низкий — вырезаем, не добавляем).

**Заменяем именование двумя дешёвыми независимыми сигналами:**
- **(a) Владелец = микрофонный стем.** `captureSource` уже считается на каждого спикера ([TranscriptionService.swift:204](meeting-recorder/swift/Sources/TranscriptionService.swift:204)). Спикер, доминирующий в mic-стеме, почти всегда — сам менеджер. Детерминированно подписываем его настроенным именем владельца. Даёт самое ценное имя (себя) бесплатно, без всякой библиотеки.
- **(b) Имена из текста на этапе саммари (идея Левона).** LLM уже читает весь транскрипт со Speaker N; инструктируем: где собеседники обращаются друг к другу по имени или представляются («меня зовут…») — сопоставь Speaker N ↔ имя. Опционально уточняется ростером из календаря (C1). **Переименовывать только при уверенности**, иначе оставить Speaker N.

**Деградация:** нет календаря → работают (a)+(b). Нет рекап-провайдера → работает (a), остальные остаются Speaker N. Пол всегда — консистентные номера.

### Шаги

- ☑ **3.1 Вырезать библиотеку голосов и раздел People.** Удалены `PeopleStore.swift`, `PeopleSheet.swift`, `SpeakerConfirmationView.swift`; раздел People убран из sidebar ([MainView.swift](meeting-recorder/swift/Sources/MainView.swift)) и из ⌘K-поиска ([SearchPalette.swift](meeting-recorder/swift/Sources/SearchPalette.swift)); вкладка Speakers (пороги/калибровка) убрана из Settings ([SettingsSheet.swift](meeting-recorder/swift/Sources/SettingsSheet.swift)); онбординг больше не просит записать голос (шаг `.voice` вырезан из [OnboardingView.swift](meeting-recorder/swift/Sources/OnboardingView.swift), остались welcome→microphone→ready). Вся matching-логика вырезана из `TranscriptionService` — `diarizeAndMatch` переименован в чистый `diarize` (диаризация → Speaker N, без эмбеддингов/cosine/порогов). Данные `people.json`/сэмплы на диске не трогали — просто перестали читать. Проект собирается чисто (`swift build`).
- ☑ **3.2 Убрать пост-транскрипционный опрос спикеров + переименование на уровне спикера.** `SpeakerConfirmationView` и вся `pendingSpeakers`/`skippedSpeakers`/`ContaminationWarning`-ветка удалены из `AppState` — транскрипт сохраняется сразу после диаризации (`await runSave()`), без ручного шага подтверждения. Ручное переименование сохранено, но на **гранулярности сегментов с массовым применением**: `AppState.reassignSegments(_:toName:)` принимает набор индексов и просто переименовывает — из панели участников (`RecordingDetailView.participantRow`) передаётся **сразу весь набор сегментов этого спикера** («Speaker 2» → имя применяется ко всем его репликам разом одним действием), а точечная правка отдельной реплики остаётся доступна из контекстного меню сегмента для редких точечных исправлений диаризации.
- ☑ **3.3 Владелец = mic-стем.** Имя владельца берётся из **онбординга** (шаг «Как вас зовут», сохраняется в `Preferences.userName`). `TranscriptionService.resolveOwnerName` детерминированно подписывает mic-доминантного спикера (через `AudioSourceEnergyClassifier`) этим именем. _Дешёвый и надёжный сигнал; не зависит от LLM/календаря._
- ☐ **3.4 Именование по тексту на этапе саммари.** В рекап-этап (Джоба 4) добавить шаг сопоставления Speaker N ↔ имя из обращений/представлений (+ ростер из C1), с порогом уверенности; результат применяется и к транскрипту, и к саммари. _Зависит от Джобы 4 и C1 — отложено вместе с ними (см. 4.7)._

## Джоба 4 — «Быстро вытащить суть встречи» (ядро ценности)

**Как сейчас:** авто-пайплайн стоп→транскрипт→save→рекап работает, окно открывается на вкладке Summary. Промпт (2026-07-27) — конспект договорённостей: Итог / Решения / Задачи / Открытые вопросы / Ход обсуждения / Прочее; заметки вплетаются по смыслу; `languageLock` append ([RecapService.swift](meeting-recorder/swift/Sources/RecapService.swift)). Саммари редактируемое. **Заголовок:** календарь при старте → иначе «Recording …» → LLM только для авто-placeholder (`titleManuallySet` не латчится на placeholder).

**Решения пользователя (2026-07-22):**

2. **Заголовок:** из календаря (C1), если есть; иначе LLM генерирует. **Плюс новые производные от LLM:**
   - **Сабтайтл-темы:** короткий список обсуждённых тем через запятую → показывается сабтайтлом завершённой встречи во вкладке Meetings (сканируемость/вспоминаемость/поиск).
   - **Авто-теги:** LLM тегирует встречу по транскрипту+саммари из **утверждённого словаря** (мульти-лейбл, 0..N). **Словарь v1 (утверждён 2026-07-22):** `1:1` · `стендап` · `ретро` · `планирование` · `дизайн-синк` · `дискавери` · `брейншторм` · `стратегия` · `клиентская` · `защита решения` · `найм` · `админ` · `внутренняя`. Тип встречи = тег → в будущем драйвит выбор шаблона. _Возможные добавки (Левон подумает): демо, воркшоп, постмортем; дробление «клиентская» по стадии._
3. **Модели:** курс на **более мощную локальную модель** по умолчанию (`llama3.2` 3B слаба для русского делового саммари). Claude/API — позже: нет командного ключа, а каждому заводить свой API = огромный фрикшен. Прийти к этому надо, но не сейчас.
4. **Шаблоны саммари — понадобятся.** Саммари должны соответствовать (а) внутренним стандартам команды и (б) рекомендациям Николая Товеровского (см. [[toverovsky-summary-ref]]); **при конфликте внутренние стандарты перевешивают**. Идеал: LLM распознаёт тип встречи (= тег из п.2) и применяет шаблон. **Пока достаточно универсального** промпта (у всего есть action items и т.п.). Дизайн шаблонов — отдельная мыслительная работа.

#### 4.5a-план — бандл Ollama (составлено 2026-07-25)

**Вердикт по «пора ли»: технически да, по срокам — не первым шагом.** Бандл упирается в подпись, а подпись сейчас — самое слабое место проекта (нет стабильного сертификата, ad-hoc-пересборки сбрасывают TCC). Второй неподписанный сайдкар усугубляет ровно ту боль, которая уже есть. **Порядок: (1) живые тесты · (2) Developer ID + нотаризация · (3) бандл Ollama.** Дешёвую подготовку из «Шага 0» можно делать хоть сейчас — она полезна независимо от бандла.

**Лицензии — чисто.** `ollama` CLI/репозиторий — **MIT** (бандл в коммерческий продукт разрешён при сохранении копирайт-нотиса). ⚠️ Официальное **GUI-приложение** Ollama под MIT **не** подпадает — бандлим только CLI. Qwen2.5-7B — **Apache 2.0** (редистрибуция ок; 3B и 72B — другие лицензии, их не брать). Нужен экран «Лицензии» в About с нотисами MIT + Apache-2.0/NOTICE.

**Почему Ollama, а не альтернативы:**
- **llama.cpp / MLX напрямую** — меньше и без демона, но это существенный новый код (GGUF, чат-шаблоны, семплинг) и потеря управления моделями (`pull`, квантизации). Не окупается.
- **Apple Foundation Models (macOS 26+)** — соблазнительно (ноль байт, ноль загрузки, бесплатно), но **дисквалифицируется контекстом**: у модели жёсткое окно в несколько тысяч токенов, а транскрипт часовой встречи в разы больше — без чанкинга не влезает. Плюс требует macOS 26, а таргет 14+. **Но:** может пригодиться позже как оппортунистический быстрый путь для **шага метаданных** (заголовок/темы/теги генерятся из короткого саммари, а не из транскрипта).
- **Ollama** выигрывает тем, что `RecapService.callOllama` уже написан и работает, а весь ops-паттерн сайдкара (спаун, health, idle-stop, PID-файл, проверка владения портом, backoff) уже выстрадан на `GigasttSidecar` — его надо обобщить, а не писать заново.

**Шаг 0 — подготовка (полезна независимо от бандла):**
1. **Adopt-if-present.** Если на :11434 уже висит здоровая Ollama (как у Левона сейчас) — использовать её и **не спаунить свою**. Иначе поднимать свою на отдельном порту (`OLLAMA_HOST=127.0.0.1:11435`) со своим `OLLAMA_MODELS`. Без этого получим ровно C8/S4 в новой обёртке.
2. **Поднять порог диска.** `checkDiskSpaceForModelDownload` требует всего 4 ГБ, а qwen2.5:7b — ~4.7 ГБ (плюс GigaAM 225 МБ). Порог занижен уже сейчас.
3. **Освобождать ASR до рекапа, а не после.** Сейчас `releaseHeavyResources()` стоит в `defer` у `runTranscribe`, то есть выполняется **после** `runSave → runRecap` — во время работы LLM модель GigaAM всё ещё в памяти. На 8 ГБ-маке (целевое железо!) это gigastt + 4.5 ГБ qwen одновременно. Освобождать надо перед вызовом рекапа.

**Шаг 1 — обобщить сайдкар.** Вынести из `GigasttSidecar` переиспользуемый слой (спаун, health-поллинг, idle-stop, backoff+cap, PID-файл, проверка владения портом) и посадить на него обе службы. Это же закрывает часть H4/A2.

**Шаг 2 — жизненный цикл модели.** `pull` с прогрессом в онбординге (UI уже спланирован в 4.5b), докачка/резюм при обрыве, состояние «рекап ждёт модель» и слив очереди по готовности. Idle-stop: `keep_alive: 10s` уже есть — при своём сервере добавить и остановку самого `ollama serve` после простоя.

**Шаг 3 — подпись/нотаризация/раздача.** Подписать вложенные бинарники Developer ID + hardened runtime, нотаризовать, проверить, что Gatekeeper пропускает. Только после этого DMG.

1. **Retention: НЕ авто-удалять, а следить за размером и предлагать.** Мелкие `.md` хранить смело (они крошечные — реальный вес это аудио/`.wav`). Периодически, если суммарный размер хранилища превышает **X ГБ**, — *предлагать* убить старые встречи. Приложение **само ничего не удаляет**.
2. **Поиск — простой, здесь-и-сейчас 99% решается.** Полнотекст по **транскриптам + саммари + заметкам** (добавить саммари в индекс). **Теги в поиск НЕ добавляем.**
3. **Фильтрация в списке встреч — пригодится** (по тегам из 4.4).

### Шаги

- ☑ **6.1 Заменить time-based retention на size-based nudge.** Убрать/выключить авто-удаление по дням. Считать суммарный размер хранилища (в первую очередь аудио); при превышении порога **5 ГБ** (DECIDE-4) — ненавязчиво предлагать удалить старые записи (список кандидатов, удаляет пользователь). Никогда не удалять само.
- ☑ **6.2 Добавить саммари в полнотекстовый поиск.** Индексировать `recap.md` наравне с транскриптом и заметками. Оставить поиск простым; теги в него не добавлять.
- ☐ **6.3 Фильтрация списка встреч по тегам.** В списке Meetings — фильтр по тегам (из 4.4). Это list-level фильтр, не часть ⌘K-поиска.
- ☑ **6.4 Крэш-рекавери — не трогаем.** Двухфазный чекпоинт (ASR → диаризация) надёжен; изменений не требует.
