# Propeller — план тестирования и метрик (надёжность + измеримость)

_Третий компаньон к [plan-v2.md](plan-v2.md) (продуктовые джобы) и [plan-optimization.md](plan-optimization.md) (энергия/стабильность). Там — что делаем; здесь — как убедиться, что это работает, и как измерять любое следующее изменение. Составлено 2026-07-24 по итогам ревью кодовой базы + сверки с практиками XCTest-метрик, `package-benchmark`, `powermetrics`/`footprint`, `os_signpost` и ASR-бенчмаркинга (RTF/WER)._

**Зачем это (две джобы этого плана):**
1. **Покрыть автотестами** — чтобы правки в пайплайне и рефакторинг под метрики не ломали поведение молча.
2. **Собрать метрики эффективности** — чтобы для каждого следующего шага можно было ответить на два вопроса: **«оптимизация дала прирост или нет?»** и **«сколько ресурса сожрёт новая фича?»**.

Обе джобы опираются на один фундамент: код должен быть **измеримым в изоляции** (швы/DI), должен существовать **фикстур-корпус** (эталонное аудио + эталонные входы) и **headless-харнесс** (прогон пайплайна без UI). Этот фундамент уже начат — `PropellerPure`, `SpeakerMatchingCore`, `Experiments`, `Checks` — план его достраивает, а не изобретает заново.

**Это две независимые дорожки — не обязательно делать целиком и по порядку:**
- **Дорожка «метрики»** имеет крошечный MVP: **F1 (сигнпосты) + F2 (одна фикстура) + M2 (батч-харнесс) + M3 (baseline+diff)**. Этого достаточно, чтобы уже завтра отвечать «помогло/нет» и «сколько стоит фича». Всё остальное в M/Q — расширение точности.
- **Дорожка «тесты»** (Блок T) идёт параллельно и защищает рефакторинг под метрики. Её можно набирать инкрементально.

Начинать имеет смысл с MVP-метрик, а тесты добавлять под те модули, которые правишь.

Статусы: ☐ не начато · ◐ в работе · ☑ готово.

---

## MVP-скоуп (с этого начинаем — минимум, дающий рабочий ответ «помогло/нет»)

Пять шагов. После них есть замкнутый цикл: снять baseline → внести правку → получить **человекочитаемый отчёт** с вердиктом. Всё остальное в плане — расширение точности и охвата.

- ☑ **F1** — сигнпосты по стадиям пайплайна (ASR / diarize / mix / recap / sidecar.spawn / release).
- ☑ **F2** — одна фикстура: короткий синтетический русский клип + стемы + эталон-транскрипт.
- ☑ **M2** — батч-харнесс: гоняет реальный пайплайн на фикстуре, эмитит метрики-JSON (RTF, spawn, peak RSS, RSS-после-выгрузки).
- ☑ **M3** — `baseline.json` + `bench-diff`: сравнение с порогами.
- ☑ **R (мин.)** — `benchmarks/report.md`: вердикт + таблицы по группам + расшифровки метрик (Блок R).

Idle/энергия (M1), тесты (Блок T), качество WER/DER (Q) — **вне MVP**, подключаются по мере надобности. Idle-харнесс (M1) стоит добавить сразу после MVP — он доказывает главный тезис «незаметен в простое».

## Принципы (на них держится весь план)

- **Functional core / imperative shell.** Чистую логику (парсинг, слияние ASR+диаризации, промпты, дебаунсы, бэкоффы, ретеншн-предикаты) выносим в библиотечные таргеты и тестируем как функции. Императивную оболочку (AVFoundation, ScreenCaptureKit, EventKit, сеть, процессы) держим тонкой и тестируем контрактно/интеграционно. `PropellerPure` — уже ровно этот паттерн, масштабируем его.
- **Instrument once, measure everywhere.** Разметить пайплайн `OSSignposter`-интервалами **один раз** — и те же сигнпосты читаются тремя способами: живьём в Instruments (`xctrace`), в перф-тестах (`XCTOSSignpostMetric`), и из `log show --signpost` шелл-харнессом в JSON. Это самый выгодный первый шаг.
- **Baseline-дисциплина.** Метрика без зафиксированного baseline бесполезна для сравнения. Каждая метрика имеет эталон в `benchmarks/baseline.json`, снятый на референс-машине; сравнение — это всегда **дельта к baseline с порогом**, а не абсолютное число из воздуха.
- **Честность про шум CI.** GitHub Actions macOS-раннеры слишком шумные для гейта по абсолютной производительности. CI гейтит **корректность** (`swift test`) и **сборку** бенч-таргета; перф-сравнение живёт на **фиксированной референс-машине** (Мак Левона) и оперирует относительными дельтами и RTF, а не миллисекундами с раннера.
- **Приватность фикстур.** В репо не коммитим реальное аудио встреч (это и так в `.gitignore`). Корпус — синтетическая русская речь (TTS) + при желании один короткий очищенный клип.

## Блок F — Фундамент (включает всё остальное)

### ☑ F1. Разметить пайплайн сигнпостами (`OSSignposter`)

Один `OSSignposter` (subsystem `app.propeller`, категории `pipeline`/`sidecar`/`idle`). Интервалы вокруг ключевых стадий:
- `sidecar.spawn` (spawn → healthy) в [GigasttSidecar.startIfNeeded](meeting-recorder/swift/Sources/GigasttSidecar.swift:118)
- `asr` вокруг `GigasttClient.transcribe` в [TranscriptionService.transcribeAudio](meeting-recorder/swift/Sources/TranscriptionService.swift:102)
- `diarize` вокруг `diarizer.process` в [TranscriptionService.diarize](meeting-recorder/swift/Sources/TranscriptionService.swift:146)
- `mix` вокруг офлайн-микса в `AudioRecorder`
- `markdown` вокруг `MarkdownWriter.render`
- `recap` вокруг `RecapService.generateRecap`
- `release` вокруг `releaseHeavyResources()` (чтобы видеть, когда память реально освобождается)

Даёт бесплатную базу для F4/M1/M2. Verbose уже за `#if DEBUG` (E6) — сигнпосты near-zero-cost, оставляем всегда.

### ☑ F2. Фикстур-корпус (`meeting-recorder/swift/Tests/Fixtures/`) — MVP: `ru-short-2spk`

- **Аудио:** 1–2 коротких (30–60 с) синтетических русских клипа (TTS, 2 спикера) + их `.mic.wav`/`.sys.wav` стемы. Полностью шеринговые, детерминированные. Опционально — один короткий очищенный реальный клип для реализма.
- **Эталоны:** `reference-transcript.txt` (для WER/CER, Q1), `reference-speakers.json` (спикеры/границы для DER, Q1).
- **Текстовые входы:** захардкоженные ASR-сегменты, транскрипты, LLM-ответы (валидные и мусорные) для golden-тестов markdown/recap без запуска моделей.

Большой корпус аудио — **вне** git (в `.gitignore`, как `phase0/*.wav`); в репо только маленькие клипы, которые не жалко.

### ☐ F3. Инструменты измерения (решено — сплит по назначению)

- **Корректность** → новый код на **swift-testing** (`@Test`/`#expect`, параметризация, `.enabled(if:)` для opt-in тяжёлых); существующие XCTest оставляем, оба гоняются под `swift test`.
- **Перф пуристых горячих путей** → `package-benchmark` (CLI/CI-натив, p90/p99, пороги absolute+relative, `swift package benchmark baseline check`). `brew install jemalloc` ставим — включает malloc/mem-метрики на macOS (wall-clock/CPU/syscalls работают и без него).
- **Тяжёлый пайплайн + idle/энергия** → **свой JSON-харнесс** (M-блок) + человекочитаемая выдача (Блок R): ни XCTest, ни package-benchmark это не покрывают.

### ☐ F4. `benchmarks/` + схема baseline + `swift test` в CI

- `benchmarks/baseline.json` — эталонные числа с референс-машины; `benchmarks/latest.json` — последний прогон; `tools/bench-diff` — дифф с порогами, печатает таблицу дельт (🟢/🔴), ненулевой exit при регрессии сверх допуска.
- В [build.yml](meeting-recorder/.github/workflows/build.yml) добавить шаг `swift test` (корректность) — гейт на каждый PR. Перф-джоб — отдельно, ручной/nightly, на self-hosted или локально.

## Блок T — Тестовое покрытие (пирамида)

### Уровень 1 — Юнит (чистая логика, быстро, детерминированно)

Вынести из executable-таргета в `PropellerPure`/новый `PropellerPipelineCore` и покрыть:
- ☐ **MarkdownWriter** — golden-тесты `renderSimple`/`renderObsidian`, `slugify`, `speakerSlug`, `extractSpeakers`, `chatClipboardText`, коллизии slug в Obsidian-vault.
- ☐ **TranscriptionService merge/format** — `mergeConsecutiveSameSpeaker`, `collapseConsecutiveSameSpeaker`, `formatTranscriptText`, логика `resolveOwnerName` (сейчас `private` в executable).
- ☐ **RecapService** — `resolveBackend` (выбор провайдера Ollama→OpenAI→Claude/Off), `metadataPrompt`, `buildUserMessage`, `wrapRecapDocument`, `stripCodeFences`, `RecapSkipReason`, `throwIfBadHTTP`.
- ☐ **SpeakerMatchingCore** — `AudioSourceEnergyClassifier.classify` (грани mic/system/mixed/unknown, `dominanceRatio`), `SourceAwareScoring.adjustedSimilarity`, `MixGain` edge-cases. Логика чистая, тестов нет — быстрый выигрыш.
- ☐ **GigasttSidecar decisions** — вынести чистые: бэкофф `min(60, 1.5·2^(n-1))` + cap 5 ([GigasttSidecar.swift:209](meeting-recorder/swift/Sources/GigasttSidecar.swift:209)), гейт health по `model != "loading"`, `progressFraction`, `modelsPresent`.
- ☐ **ZoomMeetingDetector** — вынести дебаунс-редьюсер (`enterThreshold`/`exitThreshold`: сырой сигнал → подтверждённый enter/exit) как чистую функцию состояния.
- ☐ **RecordingStore/Models** — предикат ретеншена, id-парсинг/дедуп `scanForOrphanRecordings`, Codable round-trip `RecordingEntry` (включая декод легаси-полей).

### Уровень 2 — Контракт/интеграция (реальный I/O, без моделей и сети)

- ☐ **RecordingStore round-trip** против temp-директории (load/save/orphan-scan/recover). Требует шва: сейчас читает `Preferences.shared.recordingsPath` — инжектить путь/`StorageConfig`.
- ☐ **GigasttClient contract** — поднять stub-HTTP-сервер (или `URLProtocol`), говорящий на протоколе gigastt `/health` + `/transcribe`; проверить парсинг `ASRSegment[]`, ошибки, стриминг с файла (S1). Страховка на день, когда gigastt обновит API — без 225 МБ модели.
- ☐ **RecapService contract** — `URLProtocol`-стабы для форм ответов Ollama/OpenAI/Claude; проверить сборку промпта, парсинг, `keep_alive: 10s`, извлечение метадаты, маппинг ошибок.
- ☐ **MarkdownWriter.save** в temp-vault — контент-golden + коллизии slug.

### Уровень 3 — E2E golden (медленно, нужны модели + фикстур-аудио, opt-in)

- ☐ Один канонический прогон `ASR → diarize → markdown → (stub LLM)` на фикстуре; ассерты — **инварианты** (сегментов > 0, спикеров ≥ 1, транскрипт непустой, markdown валиден), не точный текст. Гейтится через `.enabled(if:)`/env, чтобы обычный `swift test` оставался быстрым и герметичным. Это же — ground-truth для метрик качества (Q1).

**Явная цель покрытия (честно про «всё»):** «покрыть всё» = **вся чистая/решающая логика + оба сетевых контракта + один E2E-golden** + **визуальный хром** (см. ниже). Системный glue (AVFoundation/SCK/EventKit) **не** покрываем прямыми тестами — из него извлекаем логику во вью-модели/чистые функции.

**Хром / layout (исключение из «no snapshots»):** изолированные chrome-вьюхи в `PropellerUI` (напр. `MeetingsTitleBlock`) покрываем **swift-snapshot-testing** + assert midY слотов иконок. Пиксельный snapshot **всего окна** Meetings со списком — по-прежнему не делаем (шум данных). Пересъёмка: `SNAPSHOT_TESTING_RECORD=1 swift test --filter MeetingsTitleBlock` (см. `Tests/MeetingRecorderTests/README.md`).

**«Всё» — тоже метрика.** Само покрытие меряем: `swift test --enable-code-coverage` → `llvm-cov report` по библиотечным таргетам (`PropellerPure`, `SpeakerMatchingCore`, будущий `PropellerPipelineCore`). Цель формулируем как «≥ X % по извлечённой чистой логике», а не «X % по всему проекту» (последнее бессмысленно раздувается непокрываемым UI-glue). Число покрытия — ещё одна строка в тренд-логе.

## Блок M — Метрики эффективности (ядро запроса)

Два режима, ровно по тезису plan-optimization («в простое незаметен; всё дорогое — лениво, освобождается после»).

### Режим A — Idle-футпринт (фоновое «install & forget»)

Что меряем (whole-app, рантайм — не XCTest):
- Resident memory (`footprint`) в простое.
- CPU % в простое (цель ≈ 0).
- **Wakeups/сек** и коалесинг таймеров — plan-optimization весь про tolerance/гейтинг, надо **доказать**, что сработало (`powermetrics --samplers tasks`).
- Energy Impact / per-process power (`powermetrics`).
- Отсутствие power-assertions в простое (IOKit — они это уже соблюдают).

### ☐ M1. Idle-харнесс

Шелл-скрипт-сценарий (`tools/measure-idle.sh`): собрать `.app` → запустить → выждать N мин простоя → снять `powermetrics`/`footprint` K раз → записать медиану+p90 в JSON. Плюс сценарий «Zoom idle-открыт» (проверить E3: поллинг только пока Zoom жив, интервал 6 с + tolerance). Дисциплина: та же машина, тот же OS, тихая система, K сэмплов, медиана+p90 vs baseline.

**Осторожно с TCC (влияет на воспроизводимость).** Каждая ad-hoc-пересборка `.app` **сбрасывает** разрешения Микрофон/Запись-экрана/Календарь (нет стабильного сертификата — известная боль). После сброса приложение на старте может дёргать авто-перезапрос доступа — это исказит первый idle-замер. Мерить либо на уже прогретом (разрешения выданы) билде, либо сперва закрыть self-signed-сертификат «MeetingRecorder Dev» из plan-optimization, чтобы TCC перестал слетать. Baseline и сравниваемый билд снимать в одинаковом TCC-состоянии.

### Режим B — Батч-пайплайн (редкая тяжёлая работа)

На канонической фикстуре:
- **Spawn→healthy** сайдкара (холодный/тёплый).
- **ASR wall-clock + RTF** (`RTF = время / длительность_аудио`) — стандартная метрика ASR: нормализует по длине клипа (не по железу/термалу), поэтому это правильная единица **на фиксированной машине**. Тёплый/холодный прогон разделять — модель на ANE после первого прогона тёплая.
- **Diarize wall-clock + RTF.**
- **Peak RSS в батче** (GigaAM + FluidAudio) и **RSS после `releaseHeavyResources()`** — доказывает, что E1/E2 реально освобождают память (хрупкий инвариант, достойный жёсткого теста).
- Тайминги микса, markdown, LLM-рекапа (+ токены на локальном Ollama-пути).
- E2E: stop → сохранённый транскрипт; → рекап.

### ☑ M2. Батч-харнесс (`swift run -c release Bench`)

Отдельный executable-таргет (расширение `Experiments`), гоняет **реальный** пайплайн на фикстуре и эмитит метрики-JSON (читая сигнпосты из F1 + сэмплинг RSS). Плюс **микробенчи** чистых горячих путей (merge, markdown, energy-analyzer) через `package-benchmark`/`XCTest measure` с гейтом по CPU/аллокациям.

### ☑ M3. Baseline + diff-воркфлоу (`tools/bench-diff`, `tools/measure-batch.sh`)

`benchmarks/baseline.json` (снят на референс-машине) + `tools/bench-diff` (пороги, таблица дельт, ненулевой exit при регрессии). Плюс append-only лог результатов на коммит — чтобы видеть тренд во времени.

Пример строки метрики (медиана+p90 по K прогонам, порог допуска на регрессию):

```json
{
  "machine": "levon-mbp-m3", "os": "26.4", "commit": "40ae070",
  "metrics": {
    "asr.rtf":            { "median": 0.18, "p90": 0.21, "tolerance": "+15%" },
    "diarize.rtf":        { "median": 0.09, "p90": 0.11, "tolerance": "+15%" },
    "sidecar.spawn_ms":   { "median": 2400, "p90": 3100, "tolerance": "+20%" },
    "batch.peak_rss_mb":  { "median": 640,  "p90": 690,  "tolerance": "+10%" },
    "batch.rss_after_release_mb": { "median": 120, "p90": 140, "tolerance": "+15%" },
    "idle.rss_mb":        { "median": 45,   "p90": 48,   "tolerance": "+15%" },
    "idle.wakeups_per_s": { "median": 1.2,  "p90": 2.0,  "tolerance": "+30%" },
    "asr.wer":            { "median": 0.11, "p90": null, "tolerance": "+0.03" }
  }
}
```

`bench-diff` красит 🔴, если `latest.median` вышел за `baseline.median + tolerance`. Числа выше — плейсхолдеры; реальные снимаются в M2/M1.

## Блок Q — Метрики качества (не только скорость)

Ценность продукта — точность транскрипта/саммари; «быстрее» ценой качества ловить обязательно.

- ☐ **Q1. WER/CER** ASR против `reference-transcript.txt` (2–3 клипа хватит, чтобы заметить обрыв качества).
- ☐ **Q2. DER / точность числа спикеров** против `reference-speakers.json` (их же методология фазы 0: «FluidAudio ≈ 2, gigastt diar ≈ 14»).

Гейт мягкий (эти метрики шумят), но регресс на клиф — виден.

## Блок R — Человекочитаемая выдача результатов

JSON и цифры с порогами — это машинный слой. Поверх него нужен слой, который **читается как человеческий текст**: что сравнивали, что стало лучше/хуже, надо ли беспокоиться. Без расшифровок (что такое RTF, wakeups) — потому что держать это в голове не нужно.

**Две поверхности вывода:**
- **Терминал** — быстрый цветной дайджест сразу после `tools/measure.sh` (вердикт-строка + компактная таблица). Для дев-петли.
- **`benchmarks/report.md`** — полный отчёт, рендерится в любом просмотрщике (или публикуется как Artifact/страница). Для «сесть и понять».

**Правила выдачи, чтобы её реально можно было понять:**
- Наверху — **вердикт одной строкой**: ✅ Принять · ⚠️ Разобраться · ❌ Регрессия.
- Дальше — **итог человеческим языком** (2–3 предложения): что было целью, достигнута ли, что просело.
- Метрики сгруппированы по смыслу (**Скорость · Память · Простой/энергия · Качество**), а не свалены в один список.
- Каждая строка: человеческое имя · было → стало · Δ · в бюджете? · иконка · короткое «что это значит».
- Технический ключ (`asr.rtf`) прячется, показывается человеческое имя.

### ☐ R1. Рендер отчёта (`tools/bench-report`)

`bench-diff` отдаёт структуру дельт → `bench-report` превращает её в `report.md` + терминальный дайджест по правилам выше. Словарь «ключ → человеческое имя + расшифровка + направление (меньше/больше лучше)» — один файл `benchmarks/metric-glossary.json`, чтобы имена не расползались по коду.

### ☐ R2. Тренд во времени

Из append-only лога (M3) — маленькая таблица «последние N прогонов» по ключевым метрикам, чтобы видеть дрейф (медленное сползание, которое разовый дифф не ловит).

### Как выглядит `report.md` (образец — числа плейсхолдерные)

## Рефакторинг-швы (enabling — без них тесты/метрики невозможны)

- ☐ **DI вместо синглтонов.** Заменить жёсткие `Preferences.shared`/фиксированные пути в store/markdown/sidecar на инжектируемый конфиг (дефолт = shared, override в тестах). Хирургически.
- ☐ **Extract pure cores** из executable в либы (см. Блок T). Побочно снижает раздутость `AppState` (созвучно plan-optimization A2).
- ☐ **Protocol-ize сетевых клиентов** (`GigasttClient`, recap-провайдеры) — чтобы инжектить stub/`URLProtocol`.

## Рабочие процессы (ради чего всё; прямо отвечает на два вопроса запроса)

- **Оценить оптимизацию** («помогло/нет»): ветка → `tools/measure.sh` до → правка → `tools/measure.sh` после → `bench-diff` печатает таблицу дельт по метрикам. Принимаем, если целевая метрика улучшилась и ни один guardrail не регрессировал.
- **Забюджетировать фичу** («сколько сожрёт»): idle-харнесс с фичей off vs on (Δ RSS, Δ wakeups, Δ energy); если трогает пайплайн — батч-харнесс (Δ RTF, Δ peak RSS). Стоимость записываем в PR фичи. Это операционализирует «сколько фича сожрёт ресурса».

---

## Что осознанно НЕ делаем

- **Не гейтим CI по абсолютному перфу** с GitHub-раннеров (шум) — корректность в CI, перф на референс-машине.
- **Не коммитим реальное аудио встреч** — только синтетика/очищенное.
- **Не делаем snapshot всего окна / списка встреч** — только изолированный хром (`MeetingsTitleBlock` и аналоги); логику по-прежнему извлекаем в Pure.
- **Не переписываем `AppState`** — извлечение только там, где оно разблокирует тест.
- **Не над-мокаем модели** — держим ОДИН реальный E2E-golden как ground-truth; стабим только сетевые границы.

---

## Решения (зафиксировано 2026-07-24)

1. **Перф-фреймворк = сплит по назначению.** `XCTest measure`/`XCTOSSignpostMetric` для дев-петли в Xcode + `package-benchmark` для CLI/CI-гейта чистых горячих путей + свой JSON-харнесс для тяжёлого пайплайна и idle/энергии. `brew install jemalloc` — ставим (разблокирует malloc/mem-метрики в package-benchmark на macOS).
2. **Фикстур-аудио = синтетика + один реальный.** Синтетический русский TTS-клип (шеринговый, повторяемый) + один короткий очищенный реальный клип для реализма RTF/WER.
3. **Эталон перфа = Мак Левона.** Канонический baseline снимается на машине Левона; CI — только корректность (`swift test`) и сборка бенч-таргета. Авто-перф-гейт на PR (self-hosted runner) — не сейчас.
4. **«Всё» = чистая/решающая логика + сетевые контракты + 1 E2E-golden.** Вьюхи и системный glue прямыми тестами не покрываем (извлекаем из них логику). Покрытие меряем по библиотечным таргетам (см. «Всё — тоже метрика»).

## Релизная нарезка

- **T0 — Фундамент:** ☐ F1 · ☐ F2 · ☐ F3 (решено) · ☐ F4. Разблокирует всё; без него нельзя мерить то, что ты просишь.
- **T2 — Метрики (батч) + выдача [MVP]:** ☐ M2 · ☐ M3 · ☐ R1. `tools/measure.sh` + baseline + diff + `report.md` — замкнутый цикл «помогло/нет» с человеческим отчётом.
- **T1 — Корректность:** ☐ Уровень 1 юниты · ☐ Уровень 2 контракты · ☐ DI-швы. CI гоняет `swift test` на каждый PR. Идёт параллельно.
- **T3 — Idle/энергия:** ☐ M1 · ☐ R2 (тренд) + runbook «оценить оптимизацию»/«забюджетировать фичу».
- **T4 — Качество:** ☐ T3-golden · ☐ Q1/Q2. Гейт качества, тренд-лог.

Спина = **T0 + T2 (MVP) + T1**. MVP = F1 · F2 · M2 · M3 · R1 (см. секцию «MVP-скоуп»). T3/T4 — когда реально понадобятся; M1 (idle) — сразу после MVP.
